# Agent 池：节点的添加、启停与移除

2026-10-28，v1.6.5 开发候选。用户指定沿用 Key 池的操作方式。本批接续既有开放审查链，不替换生产配置或旧 Worker 的后台名单。

## 用户操作

从开发监看中心「运行总览」拓扑的「后台 Agent」列直接操作：节点上开关，点击节点打开同页设置抽屉；同列「＋ 添加节点」添加新资源，「管理 / 已移除」查看或恢复旧节点。没有独立 Agent 池页签或管理页面，旧 `/agent-pool` 页面入口已撤回（404）。Agent 名称由用户自定，调用方式由用户指定，入口和模型由用户填写；也可通过对话补齐。槽位兼容旧数据，不限定 Agent 品牌。新节点默认关闭，不读取或修改客户端登录及模型设置；只有明确测试或任务调用才执行入口，不自动探针。

点击节点查看资料、开启/关闭、带入审查表单或移除。移除将节点排除出可用池，保留来源、任务和回执，可从“已移除的节点”恢复；恢复后仍关闭。新模型/入口使用新节点，不原地改写旧任务身份。页面没有模拟节点，显示数据来自当前服务的 SQLite；没有连接时停止写入，不回退为模拟数据。

“启用”表示可接收新指派或调用，不表示客户端已启动、账号有效或模型已验证。“关闭”不杀已经运行的客户端进程；开始运行的任务可正常返回原回执，后续新指派和调用会被拒绝。

## 数据与执行边界

- 复用 `ri_sources.data`，可选 `node.version=1` 元数据记录资源和生命周期。核心 schema 7、ri_version 1、表结构不变。旧四字段来源保留原行为，首次显式切换才添加节点状态，不批量重分类历史资料。
- 每个任务卡冻结 `resource_plan`，包含节点 ID、修订号、Agent、调用方式、入口和模型；之后开关变化不改写卡片。节点状态检查同时覆盖新任务卡创建、替换第二方和后台实际执行前的事务，不只在页面隐藏选项。
- 已有专用适配器仍由可信宿主登记。CLI 可使用用户指定的 xiaoba-resource-v1 JSON stdio 入口：在明确测试或授权任务调用时执行绝对路径，不拼 shell 命令、不从网页 import 代码、不猜供应商参数。普通 CLI、桌面端与 Web 需要对应受信适配器；未接入时明确停止，不把能打开应用或网页当调用成功。
- 新节点自动后台调用需适配器声明 `supports_resource_plan=True`，并返回与任务模型一致的实际 `execution_evidence.model`；未知、未接入或模型不符直接停止，不回退到其它 Agent。
- 独立性看“入口程序＋模型”（用户 2026-10-30 裁决 6）：同一 CLI 实际路径或同一 Web 站点算同一入口，同一入口用 A 模型、B 模型算两个来源；改名称、换会话 URL 不会凑成两份独立意见。旧四字段来源没有模型资料，仍只按实际来源标识判断。更细的独立账号/实例映射尚不在本批范围。
- 事件与节点状态在同一 BEGIN IMMEDIATE 事务提交，使用修订号拒绝旧页面覆盖。相同新增/开关回调只结算一次。来源和历史没有物理删除，不能通过重复添加复活已移除节点。
- 新实现兼容旧数据；旧读者不会自动获得新开关门禁，因此部署时必须同批更新选择、执行、HTTP和界面组件，不能混合新旧调用器。降级/生产迁移仍需受审安装方案。

## 接口

| 方法/路径 | 作用 |
| --- | --- |
| GET /api/agent-pool/state | 只读节点、在途调用数和事件链；不探测模型 |
| POST /api/agent-pool/nodes | 新增，字段 node_id/name/agent/kind/interface/entry/model |
| POST /api/agent-pool/toggle | node_id/expected_revision/enabled |
| POST /api/agent-pool/remove | node_id/expected_revision；可恢复移除 |
| POST /api/agent-pool/restore | node_id/expected_revision；恢复且关闭 |

写入沿用现有 Host/同源 Origin/页面令牌/JSON 门禁。节点资料不接受凭据字段；Web 入口拒绝嵌入用户名密码及常见认证查询参数。登记、启停、移除均不会批准经验或改变认证/模型全局设置。

本批没有迁移生产库、安装页面、绑定真实模型或正式发版。B5 综合评分与自动择优仍待后续；本批允许用户显式选择已启用节点，不把该选择宣称为自动择优已经实现。

第四批对话配置、原位测试与直接调用接口见 [NODE_RUNTIME.md](NODE_RUNTIME.md)。


## 卡 20：CLI 用户在场通道（tmux，开发候选）

在添加节点中选择「CLI · 用户在场（tmux）」，登记已有 tmux 会话名和节点工作目录，入口、模型仍是用户登记资料。角色固定为 collaborator；上下文不隔离，不进入审查选择、冻结审查任务卡或独立性计票。原 cli 无人值守路径不变。

用户自行安装 tmux，并在指定会话前台打开 Agent、确认工作目录和所选模型。此通道不启动 CLI、不更改模型、不替用户确认权限；不能证明前台程序或实际上游模型。会话名只接受 1–64 个字母/数字/下划线/短横线，首字符必须是字母或数字。每个会话只允许一个等待任务。

POST /api/agent-pool/work 使用既有字段 node_id、expected_revision、task_id、step_code、instruction、materials，返回 job_id 和等待状态。任务正文只放派工卡；发送前 has-session 精确检查，send-keys 使用参数列表和 -l 字面文本，再单独发送 Enter。仅发送读卡提示；不使用 capture-pane，不解析终端，不代按权限确认。请确保会话当前前台是预期的 Agent，目标为该会话当前窗口的活动 pane。

工作目录下专用 .xiaoba-tmux-<节点ID摘要> 子目录复用 AgentWorkspace/WorkdayReceipts，保留归属、卡片、文件摘要与工作日志校验；不会接管原项目目录。发送前先落 sending 事件，发送失败/中断不自动重发，同一 task_id＋step_code 重复提交只返回原记录，变更材料则拒绝。发送后 waiting_user_agent 显示「等待用户/Agent」，不走 300 秒掉线判定。

开发监看服务每 2 秒自动校验回执，页面关闭也会收取；服务重启后继续收取已登记 waiting_user_agent 的文件，绝不重发。中断在 sending 阶段的任务保留待核对状态，由用户取消等待；不能猜测发送是否完成。回执不合格时保持等待并在页面显示原因，改好文件后自动再收，也可取消。回执、执行证据和终态写入可校验事件链；completed 只代表文件回执完成，不代表用户采用或经验批准。

页面原节点抽屉可看状态、派工卡和回执路径；POST /api/agent-pool/tmux-cancel 接受 node_id、job_id，沿用同源/Host/令牌门禁。取消仅停止收取本次回执，不向终端发信号或按键，也不会停止已开始的 Agent；迟到回执保留文件但不结算。关闭节点禁止新派工，既有等待仍保留，可显式取消。

本卡真实模型调用未授权，tmux 由用户自行安装。本次只验证隔离假 tmux，不代表真实 CLI 权限批准或真实模型执行通过。离线/临时脚本宿主可显式调用 pool.tmux.collect()；无人值守既有适配器和六个 C1 文件均未修改。

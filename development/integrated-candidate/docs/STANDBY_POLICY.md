# 三个 Agent 的等待与备用补位

用户 2026-10-20 确认：AGY、DSH 是两个主后台，标准 Qoder 的 qodercli 是备用。三者遵守相同的任务等待、输出验收、预算和审计规则；模型都用用户自己的选择（DSH 跟随桌面配置，AGY 用配置里写明的模型，Qoder 用用户在 qodercli 里上次选定的模型；没写模型或读不到就停止，不核实、不比对，路由里不得配置上游或凭据，见发布说明第五十八节）。正常任务仍需要两个不同后台的合格结果，备用只接替缺失的一侧，不增加第三票，不重审已有结论。

## 判断表

| 可观测情况 | 处理 |
|---|---|
| CLI 明确返回连接超时、DNS/TLS 错误、连接拒绝 | 记录外部故障；另一主后台已有合格结果、备用健康且满足预算时补位 |
| DSH/AGY 上游中断、ECONNRESET、socket hang up、EOF、带上下文的 500/502/503/504（如 `HTTP 503`、`503 Service Unavailable`、5xx 后紧跟网关 HTML 错误页；孤立的数字不算） | 同上；旧调用须先结束，不能边执行边补位 |
| 限流、额度不可用（含当日用量上限，如 qodercli 在结果的 `errors` 列表里给出 daily usage limit） | 记录外部故障，可以补位；不切账号、不改上游，后续重试仍有界 |
| 401/403、登录失效、缺凭据 | 报告并记外部认证故障，可以补位；不重试认证、不读取或修改登录材料 |
| 真实健康探针失败（不论原因，包括内部类别；用户 2026-10-21 定），或已记录的外部故障尚未恢复 | 派发前可用健康备用替这一侧；内部或未知故障类别的任务降级（没有探针证据）、未探针、过期或矛盾来源不能冒充探针失败；已明确记录为 external_upstream / external_auth 的失败是另一条允许来源，无须再冒充探针；构包门禁独立核对：正式验收库里只要有备用参与就必须有 `standby.substituted` 事件，被替换者必须是主后台；派发前补位（事件理由 `health_probe_failed`）时，被替换方补位前最近一条健康记录必须是失败（真实探针失败，或任务里已记下的外部故障写入的那条健康记录），且类别与事件一致；任务中途补位（事件理由 `external_failure`）时，被替换方必须在本任务有一次与事件**同类别**的失败运行，有失败运行但类别不同也拒绝。缺任何一项即拒绝 |
| 进程仍在、CLI 初始化、流式活动、任务耗时超过 300 秒 | 有真实进展则刷新无进展计时并续租；不凭总耗时换人，不仅凭PID声称上游已接单 |
| 长时间静默、只有进程存在 | 记录实际阶段和无进展时长；连续300秒无实际进展才判卡住，记为外部上游故障（用户 2026-10-20 定：本地分不清上游停算与本地挂起，统一按外部处理），先终止原进程组并回收，再按补位条件接替 |
| 进程退出、没有合格响应 | 按实际错误分类；上游空响应可补位，本地适配器缺陷/未知崩溃停止并报告，不一律视为外部故障 |
| 审查已返回合格 FAIL 或与另一侧意见不同 | 保留审查，进入原裁决流程；禁止换人争取 PASS |
| 任务中途：工具调用标记、思考泄露、验收格式错误、输出预算耗尽、其他内部故障 | 不补位，保留原失败处理及冻结/拆分流程（“内部故障不补”只适用于任务中途的调用失败；探针失败见上）。输出预算耗尽的类别仍记 `external_upstream`，但带 `output_limit_exhausted` 标记，编排器据此不补位、不写后台健康记录 |
| 备用的 CLI 本身坏了（如 qodercli 软链接断了） | 不影响上班、接单和安装：doctor 只按两个主后台判定可否接单，备用状态单独报告在 `standby_cli_routes` |
| 两个主后台都失败、备用不健康、已用过一次备用或预算不足 | 无法组成两份独立结果，停止/冻结，不能让 Qoder 充当两票 |
| 本任务已用备用替过一侧，之后另一侧探针失败 | 不再补位，任务冻结；不沿用替换另一侧的旧记录，被替换方健康记录保留探针原文 |
| 启用的主后台少于 `minimum_successful_agents`（含一个都没有、只剩备用） | 配置照常可读；上班、接单闸门和领任务前都返回配置受阻，任务留在队列——备用只替一对里的一侧，不能补足主后台 |
| 租约过期或执行权被收回 | 旧执行停止自身 CLI 进程组；不补位、不结算新执行者的任务 |

## 共用执行方式

用户进一步明确：300秒是连续无进展窗口，绝不是总任务时长。常规任务的 CLI 总截止为 None；AGY 的原生 `--print-timeout` 为 0，等待该轮真正结束。配置中的 `timeout_seconds` 保留兼容，现只用作显式健康探针的截止，不能当作长审查的总截止。三个后台共用run_cli的300秒无进展计时：首次CLI初始化、非空模型流增量、可识别执行阶段推进才刷新；重复初始化、空增量、PID、心跳、stderr日志、任意字节增长都不刷新。无进展错误采用external_upstream并先清理原进程组再返回调度器，满足另一侧合格/备用健康/预算等条件才补位；被替换的一侧必须带有真实失败证据（本次调用的外部故障，或补位前一条真实失败的健康探针记录），事件里附 `health_evidence`，构包门禁核对来源与类别一致；任务中途的内部故障一律不补，本任务已用过备用的不再补。探针只请求健康标记，不代表实际长任务已经完成。

现有后台 worker 等待同一调用，每至多 5 秒（且小于租约的三分之一）回调一次：每次都只读核对当前 task attempt 仍持有租约，失去即停止 CLI、不补位；只在剩余租期少于一半时才续租并写 `task.lease_renewed`；`agent.progress` 事件只在首次、阶段变化、活动增加且距上次写入满 30 秒、或静默满 60 秒时写入，进度回执文件则每次更新（v1.6.5 降频，阈值为 orchestrator 常量）。心跳、续租与事件写入都不刷新无进展计时。进度只保留阶段、PID、累计字节数、活动事件数和耗时，不保存输出正文、思考或认证信息。进度回执没有结果 ID，不能算成功。健康探针仍有界；失败不自动重探，冻结任务不自动恢复。

Qoder 用 stream-json 提供中间进度，只有一份最终 result、正文和实际模型校验都通过才算完成。CLI init 只表示本地就绪；模型相关流事件只表示观察到活动，不能保证上游正式受理或最终成功。若CLI不暴露中间进展，300秒只能表示本地连续未观察到进展，不能证明上游实际上停止计算；回执必须诚实描述这个边界。

补位前原调用已经返回错误或被显式探针截止清理；保留健康主后台结果，不给它重复派单。补位仍受原任务调用预算、每任务一次限制、同一冻结源码、B19 合格输出和 B20 恰好结算一次约束。事件、通知、实际模型及被替换方必须留痕。没有新建队列、常驻看门狗或上游接管器。

当前 Qoder 适配器禁用工具，仅可承接不需要工具、联网能力或按原 Agent 名冻结分工的审查。带能力要求和命名协作分工的任务继续按原契约停止，不能假装换一个变量即可具备同样能力。

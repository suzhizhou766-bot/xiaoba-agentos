## 监看中心启停统一使用配置端口（卡 75A）

- 启动脚本不再把端口回退写死为 8799 并显式覆盖配置：默认从 `monitor.json` 读取端口，`XIAOBA_MONITOR_PORT` 环境变量仍可显式覆盖；解析出的有效端口显式传给运行进程，使健康探测、监听、打开页面指向同一端口。
- 非法或不可读配置在探测/建日志/拉起进程之前失败，不回落 8799，也不会误启动到另一端口。
- CLI `--port 0` 显式拒绝（判断用 `is not None`，不再按真假值漏检）。
- 关闭脚本走**同一套解析规则**，启停两端端口一致。
- 不改动线上 8799 的既有进程：验收期间线上 pid 全程未变，测试只用临时端口与 `XIAOBA_LSOF` 包装器。
- **不新增 launchd 或开机自启**，启动方式仍由用户手动调用脚本；长期是否改 launchd 仍只是待议方案，不在本版范围。

## 接入口已提交回执的登记恢复、死信保留与稳定意图确认（卡 75C）

- 业务事务提交后、侧车入队前的窄窗口：待登记行写入同一业务事务；提交成功后回调/恢复路径补登记；事务回滚、提交前退出不产生悬空引用。
- 队列已写、确认前崩溃：pending 保留，恢复批次限量；重复重启与并发恢复不得重复结算。
- 死信：连续失败达到上限后**保留在库内**死信状态并告警，需显式重试；不再把“库内仍有行”误报成侧车 `reference_dead` 一类已丢引用。
- 稳定意图身份：生产者把待登记行 `id`（生产路径为 `identifier()` → uuid4）经 `reference_id` 写入队列；消费者在 flush 的同一 SQLite 事务内：
  - 已见同一 `reference_id` → 只消费文件；
  - 同内容合并且不新增 `output_recorded` → 写入 `workday.reference_acked` 作持久确认（含被合并意图）；
  - 无 `reference_id` 的旧队列 → 保留连续内容判重，合法 A→B→A 仍记三次。
- `reference_id` 纳入完整 `canonical(ref)` 敏感扫描，不作豁免；空白/控制字符/超长令牌拒绝。

以下四补丁已由用户提交为 a16037d，本轮发布一并包含；本段只补齐已有改动的发布范围，不新增运行代码。

- **J2：三项小修。** 技能 `catalog.json` 经同目录临时文件与 `os.replace` 原子替换，写入失败保留原 catalog.json 内容并清理临时文件；这是目录文件原子替换，不宣称整个多文件发布事务原子化。监看主页发送 CSP，按用户确认，自定义数据源仅连接本机同源 HTTP/WebSocket，导演台、3D 台及已声明字体资源继续使用各自策略。接入口待登记队列为空时先只读判断、不取写锁；有待办时仍进入写事务并保留全事件链校验。
- **J6：测试临时文件不污染调用目录。** 测试夹具使用受控临时目录与独立环境，补齐防回归检查；不把测试清理改动描述为生产数据清理。

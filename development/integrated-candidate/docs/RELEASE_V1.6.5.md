# v1.6.5 候选：全面检查修复、备用后台与后台等待规则

基线为已上线 v1.6.4。来源：2026-10-20 主力全面检查（`私人助理/工作区/小八AgentOS-全面检查-20261020/检查报告.md`），用户同日要求修复并走完整发版流程。

## 一、`install-service` 不再自行备份

过去重装后台服务时，命令会不问用户就把整个数据库复制到 `.runtime/backups/database/`、把原服务配置复制到 `.runtime/backups/launchd/`，违反“没有用户直接、明确的备份要求不得新建备份”（B03）。

现在：
- 服务配置的原内容只读进内存，安装失败时从内存写回，不再生成备份文件。
- 数据库已是当前结构（不需要迁移）时，命令不动它，也不备份。
- 数据库确实需要迁移时，命令停下并说明：迁移前要先备份，而备份须用户明确授权；用户同意后加 `--backup-database` 重跑，才会备份再迁移。备份是一个独立文件：复制后切回普通日志模式、清掉这份副本自己的 -wal/-shm；复制或校验中途失败时删掉这次写了一半的副本，已有备份不动。
- 初始化或校验失败时，只有确实创建过授权备份才恢复数据库；未创建时仅执行原服务恢复步骤，错误提示明确“未创建数据库备份”，不再误报“已恢复备份”。
- 重建 Runner 时，旧 Runner 先移到目标旁边的 `.小八 AgentOS Runner.previous-…`（在本次构建的临时目录之外，用于失败时放回）；替换成功后移进废纸篓（可恢复），不再留在 `.runtime/backups/runner/`；移不进废纸篓时留在运行目录并在结果里写明；替换失败、放不回原处时留在 `.previous-…` 并在报错里写明位置，绝不静默删除。（最终行为见第二十一、二十二节的两次修正）
- `agent-enable` / `agent-disable`（同一类问题，用户 2026-10-20 要求一并修）不再把配置复制到 `.runtime/backups/config/`；新配置先写临时文件再整体替换，失败时旧文件不受影响。
- 日志轮转、安装失败的新配置文件仍移到 `.runtime/backups/` 下，那是移动现有文件，不是复制备份。“安装失败的新配置”指已经替换到 LaunchAgents 位置、随后启动失败的那份（由回滚步骤移走）；替换之前写到一半的临时文件 `.plist.agentos-new` 不是安装过的配置，失败时直接清掉，生成它的原文件仍在。

新增 `tests/test_install_service_no_backup.py`，五项标到 B03。

## 二、发布目录设为只读

线上发布目录对当前用户原本可写。任何在里面运行或导入 Python 的进程都可能留下字节码缓存；入口的发布校验核对完整文件集合，多一个文件就判失败，小八拒绝运行。全面检查时就因此出过一次约两分钟的故障。

现在固定切换命令在切换成功、读回通过后，把新发布目录设为只读（文件 0444，可执行文件与目录 0555），结果写在 `release_sealed` 里；封不上只报告、不退回已成功的切换。`doctor` 新增 `release_read_only` 字段报告当前发布目录是否只读，只作报告，不改变 `ok`（测试环境的发布目录本来就可写）。新增一项切换测试标到 B08。

## 三、数据库连接显式关闭

`with sqlite3.connect(...)` 只提交、不关闭连接，Python 3.14 会报“连接未关闭”。包内运行代码 `cli.py` 的数据库备份函数 1 处、测试里 9 处，共 10 处改为 `closing(...)`；测试里原本依赖退出时提交的写法保留提交（`with closing(...) as conn, conn:`）。

**本版没改的一处：** 裁决页面后端 `review_ui_assets/server.py` 有同样写法。它是包外资产，要靠 `review-ui-install` 按清单哈希安装；而线上监看中心页面 `xiaoba-monitor.html` 自 v1.6.2 安装后已被改动，与清单两边哈希都不符，安装器会拒绝整次安装。要修这一处，得先由用户决定如何处理监看页面的改动，登记为下一版待办。这几处连接在函数结束时会被 Python 自动释放，不会累积。

## 四、备用后台 qodercli（用户 2026-10-20 要求并进本版）

AGY、DSH 仍是两个主后台。新增备用后台 `qoder_review`（本机 qodercli），平时不参与，只在某个主后台不可用时公开补位；何时补、何时不补以下列条目和 `docs/STANDBY_POLICY.md` 判断表为准。由 DeepSeek（适配器、线路、配置）、Qwen 3.8 Flash（补位调度、接单闸门）、Gemini 3.8 Flash（上班探针、构包门禁）按任务卡实现，主力核对、集成。模型来源见第十四节（用户 2026-10-20 最终定为：用用户在 qodercli 里上次选定的模型）。

- 模型来源：`selection: qodercli_settings`，读取 `~/.qoder/settings.json` 里用户在 qodercli 上次选定的模型及其思考强度，以 `--model`、`--reasoning-effort` 单次传入；用 `--setting-sources project,local` 在空目录中排除其它用户设置的干扰。读不到明确模型、思考强度不支持，或返回 JSON 缺实际模型证据、实际模型与选定的不同，均不计成功。

- 何时补：主后台健康探针未通过，或本次调用遇外部故障（`external_upstream`、`external_auth`：超时、限流、503、断连、上游空响应、认证失败）。空响应保持与现有 AGY/DSH 适配器一致的分类；工具调用文本、验收格式错误及思考泄露属于内部无效输出，不靠“可重试”属性推断为外部故障。
- 不补（任务中途）：内部故障、输出预算耗尽、思考过程泄露、主后台已给出结论（包括 FAIL）、两个主后台都不可用、启用的主后台少于两个、本任务已补过一次。（健康探针真实失败则不论原因都补，见第十五节）
- 共用等待与接替：按用户最新纠正，三个后台的常规任务均取消总时长硬截止，AGY 原生等待为0，Qoder输出stream-json；仅显式健康探针使用原配置截止。安全进度回执不算成功，按task attempt续租避免长任务被重复认领；丢失执行权停止旧CLI且禁止补位/结算。完整故障矩阵与边界见 `STANDBY_POLICY.md`，不以总耗时判失败；连续300秒无实际进展才判卡住，心跳/PID不刷新计时，原进程组先回收再补位。
- 探针来源：内部或未知故障类别的任务错误写出的 `degraded` 不等于真实探针失败；这种记录没有探针证据时不补。健康闸门和派发共享来源判定，只接受真实失败探针元数据，或已明确记录为 `external_upstream` / `external_auth` 的外部故障；后者是独立允许来源，无须再有探针标记。分派前补位事件带 `health_evidence` 白名单，构包同样检查来源与故障类别一致，不凭 `reason: health_probe_failed` 单一标签放行。本条修复第8轮实测发现的内部降级跨任务触发备用问题。
- 只读：qodercli 以 `-p`、`--tools ""`、`--no-session-persistence`、`--strict-mcp-config` 加空 MCP、`--settings '{"disableAllHooks":true}'` 在临时空目录运行；同时排除用户设置来源。它把“想调用的工具”写成正文时判为无效回答。DeepSeek 对原命令的诱饵文件实测见其回执。
- 留痕：每次补位写 `standby.substituted` 事件、在结果与裁判记录里标明、通知用户；被补位的主后台记为 `external_blocked`，后续任务在分派前就换成备用，直到用户下次“上班”的真实探针恢复它。
- 发版验收：可以计入备用补位的结论，构包门禁要求补位证据、被替换者是主后台、原因是外部故障或真实失败的健康探针（第十五节起探针失败不论原因），并在验收记录里逐份标明。（本节是最初设计；与后续各节不同处以后续各节为准，尤其第十五、二十一、二十八节。）
- 规则改写（用户同意）：“失败不静默换账号或启用其他后台”改为“不静默……；唯一例外是公开、留痕、有边界的备用补位”，入口技能卡、架构说明与第二大脑治理模板同步。
- 配置：发布包的配置模板带 `qoder_review`；线上生效配置由切换命令之外的一步登记（切换命令按设计不改后台线路），见 `docs/OPERATIONS.md`。没有备用的旧配置行为不变；启用的主后台少于两个时配置照常可读，但接单闸门挡住。

## 五、并行连接的竞态（v1.6.4 起就有，本版修复）

主力集成时复现：一个任务的两个后台在不同线程里同时访问数据库，一个线程关闭连接后 SQLite 删掉 `agentos.sqlite3-shm`，另一个线程恰好在给它改权限，第二次读权限时抛 `FileNotFoundError`，那一侧被当成未知内部故障、任务可能因此冻结。v1.6.4 期间那次原因不明的偶发失败（`internal_unknown_candidate`）很可能就是它。现在文件在检查途中消失就跳过（它已不需要加固），其余权限检查不变。新增 `tests/test_store_sidecar_race.py`，其中并行连接一项在旧代码上实测失败、新代码通过。

## 六、内部降级不能冒充探针失败

新增共享的 `standby_health` 来源判定。内部或未知故障类别的任务降级（degraded）如果没有探针证据，不能算“探针失败”；仅有未探针状态也不补位。真实探针失败，或者已经记录在案的外部故障，是两条独立的分派前补位来源；外部故障分支不要求再有探针标记。补位事件里带上 `health_evidence`，构包门禁会核对来源和类别是否一致。完整判断表见 `docs/STANDBY_POLICY.md`。

## 七、三个后台共用的等待规则（用户 2026-10-20 定）

AGY、DSH、Qoder 都不设整项任务的总时长截止。只有**连续 300 秒没有实际进展**才判失败。算进展的只有两种：非空的流式增量，以及明确的阶段推进。进程还活着、心跳、续租、重复的状态行，都不算。判定失败后，先回收原来的 CLI 进程组，再按补位规则处理。显式的健康探针另有自己的有界截止时间。租约按 task attempt 续；某个 attempt 失去执行权后，它本地的旧进程组会被停掉，不再补位，也不结算。

## 八、旧 Runner 留在原处时的提示不再丢失

第11轮 DSH 审查查出：重建 Runner 时，如果旧 Runner 进不了废纸篓、只能留在运行目录，`_build_runner_app` 会生成一句"留在…，请用户处理"，但 `_install_service` 把它丢掉了，用户看不到。现在这句提示会作为 `previous_runner` 写进 `install-service` 的结果，并新增了测试覆盖这条回退分支。

## 九、DSH 与 qodercli 的真实进度信号

（由 DeepSeek 按任务卡实现，主力核对，有真实调用实测记录。）

- qodercli：不加开关时，从启动到生成结束 stdout 一直没有输出。现在加了 `--include-partial-messages`，生成过程中会持续输出非空的 text/thinking 增量（实测间隔 0.2–0.4 秒），最终的 result 行和答案解析不变。
- DSH：`--json` 模式在它的源码里关掉了 token 级的流式输出。现在能认出的是：开局的 `session`（表示就绪），`tool_call`/`tool_result` 和 `step_start`/`step_end`（阶段推进），以及非空的 `thinking`（模型产出）。**一个生成步之内仍然没有信号**，单步超过 300 秒会按规则判为无进展。用户决定规则不动，改为把发版审查的题面拆小：每份不超过 32KB，冻结脚本强制检查。

## 十、进度事件与租约续期降频

（由 Qwen 按任务卡实现，主力核对。）

- 每次进度回调仍然只读地确认"这个 attempt 还持有租约"，一旦失去，就停掉 CLI，不补位。
- 只在剩余租期不到一半时才续租，并写一条 `task.lease_renewed`。
- `agent.progress` 只在以下情况才写：第一次回调、stage 变化、activity 增加且距上一次写入已满 30 秒、静默满 60 秒。
- 进度回执文件每次回调都会更新。
- 测试 `test_progress_event_rate` 用假时钟模拟 600 秒、121 次回调：`agent.progress` 限在 15–22 条，租期 1800 秒内不续租（降频前每 5 秒各写一条，约 242 条）。

worker 被强制结束后，任务仍要等租约自然过期才会被回收，最长还是约 30 分钟，没有变差。顺带修了一个基线缺陷：orchestrator 用到了 `PermanentAdapterError`，但没有导入，续租失败时实际抛的是 NameError。

## 十二、第16轮审查查出的测试缺陷

`tests/test_cli_progress_signals.py` 里有 4 处"进度不得带出正文"的检查，是对 `json.dumps(updates)` 的结果找中文。`json.dumps` 默认会把中文转成 `\u` 编码，所以这 4 处检查永远不会失败。修复如下：

- 这 4 处改成 `json.dumps(updates, ensure_ascii=False)`；
- 假 CLI 改为像真实 CLI 一样直接输出 UTF-8 原文；
- 新增一条直接断言：进度里只能有白名单字段，`stage` 只能是三个已知阶段之一，其余字段只能是数字。

用三种故意泄露做了验证：多加一个字段、把原文拼进 `stage`、把原文塞进白名单里的数字字段。三种都会让新检查失败；而改之前的写法，其中两种完全测不出来。产品代码没有改。

## 十三、故障分类的两处修正（第17轮审查查出，线上 v1.6.4 同样存在）

- **Headroom 就绪判断提前。** 原来，一条同时写着 AGY/Antigravity 和 headroom、unavailable 的错误（例如 "agy headroom unavailable"），会先进入"上游容量"分支，被分成 `external_upstream`。本版有了备用补位，这样任务中途的内部故障就可能被当成外部故障去补位。现在先判断 Headroom，归为 `internal_headroom`；不含 headroom 字样、但写明 AGY/Antigravity 不可用（unavailable）或容量不足的故障仍归外部上游故障；其它认不出的文字（比如适配器或解析内部错误）照旧归内部未知，不补位。
- **单独的 "EOF" 归为外部上游故障。** 原来的词表只认带前导空格或冒号的 eof，错误信息只有 "EOF" 时会落到内部候选。现在按整词匹配 eof，归为 `external_upstream`，与 "unexpected eof"、"read: EOF" 一致；只是字母里含 eof 的词（例如 eofmarker）不受影响。
- 两处各补了测试，这些测试在第17轮的旧代码上都会失败。

## 十五、任务卡并行预审后的一批修正（2026-10-21）

第20轮正式审查查出 4 个问题，用户要求停掉审查，把剩下的工作拆成 10 张任务卡并行做（DeepSeek、Qwen 3.8 Max、Qwen 3.8 Flash：4 张修复、6 张预审），再由主力统一集成。

## 五十八、发版前收尾：AGY 模型写进配置、封装档位、切换后动作（2026-11-01，卡 27/28/29）

用户 2026-11-01 裁决：配置里的模型名就是实际使用的模型；节点配置由用户自己设，连通测试通过即可。小八只读节点配置、调用 Agent、发任务卡、读回执，不核实模型。第十四节的口径到此为止，历史正文照原样保留。

**代码改了什么**

- AGY 的模型来源从"读 agy CLI 的设置文件"改为用户写在节点配置里：`cli_routes.local_agy` 只允许 `driver / selection / model` 三个字段，`selection` 固定 `configured_model`，`model` 写实际使用的模型名（候选配置里是 `Gemini 3.8 Flash (High)`）。小八不查模型目录、不读默认模型、不做模型比对，也不核实实际作答的是哪个模型；`model` 缺失或值像命令行开关时拒绝发起调用。旧写法 `agy_cli_settings`、`local_account` 仍能通过配置校验（切换前旧配置照常加载），但 AGY 调用会被拒绝并写明怎么迁移。
- 执行回执不再写"模型核对结果"（`model_verification`）这类字段，`model_source` 记 `node_configuration`；改动前写入、带这个字段的旧回执仍能读取。
- `CAPABILITY.json` 为 Antigravity 补声明 `gemini-3.8-flash-high`，与 `gemini-3.8-flash-low` 逐字段相同（reasoning、coding、long_context 为真，shell、filesystem 等仍为假）——补声明不放宽权限。未声明的推理档能力仍是 unknown，路由不会当成可用。
- 用户在场通道派卡前先做只读窗格核对：`has-session` 精确检查会话，再用 `display-message -p` 读 `#{pane_current_command}` 和 `#{pane_current_path}`；前台仍是 shell、或窗格目录与节点登记目录不同，就拒绝发送并报出实际值，此时既不建工作文件也不落 sending 记录。核对通过才用参数列表加 `-l` 字面文本 send-keys，再单独发 Enter；不使用 capture-pane、不解析终端、不代按权限确认。卡 28 实测：Enter 未被吞、约 7 秒起有输出、回执文件在同轮结算。

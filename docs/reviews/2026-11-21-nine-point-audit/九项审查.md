## 1. 实际目标、不变量与本轮根因

控制流可以收成三条，不互相替代：

- 任务与经验：宿主或协作节点做完，回执进统一入口；有经验才送审查和评分；交付后归档、复验、复用分可以同时发生，但同一任务加成品版本只结算一次。状态在 `development/integrated-candidate/src/xiaoba_agentos/store.py` 和 `experience_loop.py`，编排在 `orchestrator.py`。
- 发布：候选源码、清单哈希、部署前一版绑定、切换脚本要一致。绑定检查在 `scripts/switch_release.py`。
- 监看：用户运行 `启动监看中心.command` / `关闭监看中心.command`。活动实现在 `architecture-package-20261027/shared/工具/小八监看/`。`monitor/` 是 v1.6.1 定版快照，不是这条活动链。

本轮不把“系统只有一个根因”当作前提。30 天里反复被改的是结算和评分（`store.py` 18 次、+3243/−174），监看启停是 v1.6.15 才集中修改的一条边。两条都真实，但只有监看这条在当前 HEAD 上还能用云端解释器直接复现一个错误判定。

复现：活动树 `xiaoba_monitor.py` 的 `supervise()` 在基线里读 `run/supervisor.pid`，`os.kill(pid, 0)` 成功就打印“看护进程已在运行”并返回 2。把当前解释器自己的 PID 写进临时 pid 文件也会走到这句。该进程的命令行不是 `xiaoba_monitor.py --supervise --port <端口>`。关闭脚本基线第 18 行在同样的存活检查之后执行 `kill "$(cat "$PID_FILE")"`，会向这个 PID 发 SIGTERM。

这和 J10 已经写进启动脚本的规则冲突。`a16037d`（2026-11-13）给 `supervisor_running` 增加了目录、`--supervise` 和精确端口三道核对，服务健康但身份不符时启动失败，并且不结束那个健康服务。Python 入口和关闭脚本没有改用这道核对。字符串“看护进程已在运行”来自 `b655dff`（2026-10-27），关闭脚本的无条件 `kill` 也从那时就在。

因此本轮最小修复是把判定收成一个函数，启动、关闭和 `supervise()` 都调用它。四态是 `match`、`other`、`unknown`、`stale`。只有 `match` 才拒绝第二次启动，也只有 `match` 才发停止信号。`unknown` 不发信号、不启动第二个。`stale` 不发信号，端口空闲时允许继续启动。Linux 上命令行读 `/proc/<pid>/cmdline`；没有 `/proc` 时用 `/bin/ps -ww`。参数里含空格导致路径被拆开时返回 `unknown`，不把它当成无关进程。脚本路径先解析符号链接再比较：启动脚本留下的是逻辑路径，入口自己用 `Path.resolve()`。macOS 上 `/var` 指向 `/private/var`，临时目录会走这条分叉。比较本身已在 Linux 的临时符号链接上验证；macOS 启停仍未跑。

不把这件事写成“监看经常杀错用户进程”。本轮没有用户 Mac 的生产日志。证据是代码路径和可重复测试，不是事故计数。

## 2. 重新定义问题

用户要的是：监看要么由当前目录、当前端口的看护进程负责，要么明确说做不到，并且不要误伤别的进程。症状有三层，手段不能混用。

- 底层需求：监管身份和停止对象是同一个进程。
- 症状：云端启停测试失败。本轮实跑 `test_close_script`、`test_j10_supervisor`、`test_card75a_port`、`test_card69_detach` 共 29 项，3 失败、23 错误。失败停在固定解释器不存在；错误停在测试夹具调用 `/usr/sbin/lsof`，而这台机器的 lsof 在 `/usr/bin/lsof`。这是环境症状。
- 不该当成修复手段的事：把固定解释器改成 `sys.executable`，或删掉“不得碰 8799”的断言，让上述 29 项在 Linux 变绿。固定解释器写在 `development/integrated-candidate/src/xiaoba_agentos/interpreter.py` 和 `docs/RELEASE_V1.6.3.md`，是发版约束。

更值得先修的是身份判定，因为它在固定解释器存在时仍然会误杀或误拒。不该改的部分：v1.6.1 的 `release/` 与 `monitor/` 快照、部署前哈希绑定、经验“一次结算”和“审查不拦截宿主交付”、关闭脚本在 lsof 不可用时退出码 0 的现有测试契约。最后这条见 `test_close_script.py`：探测失败要打印“查不了”，退出码仍是 0，标准输出不得出现“已关闭”。只看退出码的自动化仍会把“查不了”和“已关闭”看成同一种成功。这是保留下来的设计，不是本轮漏改。

`RELEASE_V1.6.15.md` 写明库内死信没有页面或 CLI，默认恢复不重试死信。那是已披露的缺口，不是本轮新发现的结算错误。没有为它加入口。

## 3. 二阶和三阶影响

采用同一判定函数之后：

- 其他模块：AgentOS 队列、经验库和发布切换的代码没有改。监看活动树的启动、关闭和 `supervise()` 改了。冻结快照 `monitor/关闭监看中心.command` 仍是旧的无条件 `kill`，那份文件不随候选发布。
- 用户操作：PID 文件指向无关进程时，关闭不再杀掉它，并在标准错误说明判定。端口上由 lsof 确认的监听进程仍会按原脚本结束，这一支没有改。身份读不到时，启动不再悄悄再拉一个看护。
- 复杂度：多了一个四态函数和一次额外的 Python 启动（脚本在已有 `--resolve-port` 之外再调用一次分类）。等待循环最多约 40 次。本轮微基准只说明单次分类大约 31 微秒，相对 `kill -0` 的 0.35 微秒；脚本级的进程启动成本没有在 Mac 上量过。
- 维护：以后改身份规则只改 `classify_supervisor_process`。测试锁住启动和关闭脚本都出现 `--classify-supervisor-pid`，并且关闭脚本不再包含 `kill "$(cat "$PID_FILE")"`。
- 迁移与回滚：不改 pid 文件格式、不改 `monitor.json`、不改数据库。回滚就是回到基线这四个文件的行为：再次把存活 PID 当成看护。没有数据迁移。

若改走更大的方案（把监看并进 `development/`、删掉日期目录名、让测试在 Linux 上替换解释器），三阶影响是发布清单、架构拓扑路径和 Mac 验收夹具一起失效。本轮不做。

## 4. 可迁移机制与适用边界

只用到和这条缺陷同构的机制。

- 进程监管：PID 文件是弱引用。存活检查回答“这个号还有人”，不回答“是不是当年那个看护”。systemd 用 PID 加启动标识，这里用命令行里的脚本路径、`--supervise` 和 `--port`。适用边界：命令行能完整读到。读不到就停，不猜测。
- 分布式里的“未知不是失败”：lsof 三态已经在 `portprobe.py` 落地。监管分类沿用同一边界：`unknown` 不得执行有副作用的恢复。不要把它推广成“所有空结果都要重试”。
- 控制理论里的传感器失效：执行器在测量无效时保持，不把无效测量当成零。对应“不发信号、不第二个启动”。没有使用控制器参数或回路增益。
- 事务：身份分类不是数据库事务。它不提供崩溃后的原子切换。两个启动脚本同时看到 `stale` 仍可能竞争 pid 文件，这是原先进程已退出时就存在的窗口，本轮没有加文件锁。
- SRE：错误预算和 PR 耗时都不能代替这次函数级测量。仓库没有测试 CI，见第 8 章。

## 5. 反方与被放弃的选项

最强反证有三条。

1. 端口已经健康时，启动脚本从 `a16037d` 起就不会把无关 PID 报成“已开启”。J10 测试覆盖的是这条。本轮缺陷不在“健康服务被报成启动成功”，而在端口未就绪时 Python 拒绝启动，以及关闭脚本发信号。
2. 复现使用的是测试进程自己的 PID，不是从生产日志里抓到的一次 PID 复用。机制成立，发生频率未知。
3. 分类依赖命令行。macOS 上没有 `/proc/<pid>/cmdline`，走 `ps -ww`。本轮没有在 Mac 上执行这条回退，不能声称 Mac 的 `ps` 输出已被实测。

比较过的选项：

| 选项 | 结果 | 放弃或采用的理由 |
|---|---|---|
| 最小修复：一个分类函数，只有 match 能启动拒绝和停止 | 采用 | 能在 Linux 上复现和回归，不改解释器、清单和快照 |
| 维持现状 | 不采用 | 关闭脚本会向 pid 文件里的任意存活进程发 SIGTERM，与启动脚本注释相反 |
| 只改 Python、不改关闭脚本 | 不采用 | 误杀在关闭路径，只改启动会留下更严重的一半 |
| 让启停测试在 Linux 上改用 `/usr/bin/lsof` 和当前 Python | 不采用 | 会绕过固定解释器约束；75A 包装器禁止误探 8799，改动面大于这条身份洞 |
| 拆 `store.py`、加死信 CLI、删除 `monitor/` 快照 | 不采用 | 没有这条身份洞级别的新复现；快照被 README 和哈希清单引用 |

证伪方法：在 Mac 上用固定解释器跑 `tests.test_j10_supervisor`、`tests.test_card75a_port`、`tests.test_close_script` 和 `tests.test_supervisor_identity`。另做一次手工：把无关存活 PID 写入临时副本的 `run/supervisor.pid`，关闭脚本不得让该进程消失。若 Mac 上 `ps -ww` 把带空格的真实路径拆坏后返回 `match`，本修复在该路径上不成立。

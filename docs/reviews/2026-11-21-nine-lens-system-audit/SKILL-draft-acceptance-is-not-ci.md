# 验收轮次不是编译器

## 触发条件

出现以下信号时先停：

- 验收 FAIL 的主因是“说明与代码不一致”“入口文档口径旧”“拓扑待办与实现表述冲突”
- 同一版本候选连续第 2 轮及以上仍在修文档对齐
- 准备再开一张“热修卡”且改动可在无真实 CLI 的环境下判定对错

## 已付过的学费（仓库内）

- v1.6.12：一夜四轮（功能 → 旁路 → 八缺陷 → DSH 两缺陷），其中多轮含说明/边界对齐。
- v1.6.13：专门修第一轮验收的两条“说明与代码对齐”阻断。
- 近 14 日 GitHub PR 几乎秒合；真正的墙钟浪费在审查轮次，不在合并队列。仓库没有产品测试 CI。

## 检查步骤

1. 把 FAIL 条目分成三类：`behavior`（真机行为）、`contract`（文档↔代码）、`env`（解释器/lsof/本机路径）。
2. `contract` 类：在合入前写成 `unittest` 或检查脚本（禁止过期句、断言关键 API 文案、门适用范围）。
3. `env` 类：标明“云端不能替代 Mac”；不要为绿而改发版约束。
4. `behavior` 类：才值得交给外部审查员或真机演练。
5. 同一意图不要在长寿命分支上无限追加热修；契约测通过后再约审查。

## 证据要求

- 记录：本轮 FAIL 条目分类表；哪些已沉入测试。
- 不得把 Dependabot 依赖图耗时或 PR 打开秒数写成“性能优化成果”。

## 边界

- 不取消用户要求的双审与终审。
- 不宣称本地测试覆盖全部 CLI 厂商行为。
- 与 `gate-scope-minimum`、`authority-layers` 配套使用。

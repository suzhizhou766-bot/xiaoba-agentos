## 1. 第一性原理：本质是什么，根因是什么

### 1.1 本质循环（去掉品牌名后仍成立）

```
用户目标 → 宿主执行 →（可选）协作节点 → 交付
                ↓
        有无值得保留的经验？
         /              \
       否：结束        是：审查评分 → 用户初审 → 真实任务复验 → 用户终审 → 第二大脑复利
```

这不是通用“Agent OS”。操作系统隐喻容易把人带向：更多适配器、更多槽位、更多编排。真正产品是：

- **用户是唯一规范制定者**（已写进治理与拓扑）
- **交付是结算锚点**（一次任务+成品版本只结算一次）
- **经验必须可追溯、可复验、可废止**（审查与两阶段审批）
- **后台是可插拔劳动力池**（审查 / 协作角色，不绑定品牌）

### 1.2 最本质的系统问题（不是再缺一个功能）

把 30 天提交、验收返工、文档冲突叠在一起，根因收敛为三件事：

**A. 权威分裂**  
意图在拓扑，实现在 `development/`，线上在本机运行根，规则在第二大脑，快照还在 `release/` 与日期目录里。Agent（含本仓库的自动化）经常改到“看起来像现行”的那一层。PR #60 已证明：活动监看不在 `monitor/`，而在日期包名目录下。

**B. 验收在扮演编译器**  
没有产品测试 CI（只有 Dependabot 依赖图）。正确性依赖 Qoder/DSH 多轮验收 → FAIL → 热修卡 → 再验收。v1.6.12 一夜四轮（卡 62→64→65→DSH）是典型。

**C. 高仪式状态机覆盖过宽**  
经验核验（初审→两轮隔离验证→终审→复用改动终审→长期未用）对“值得进第二大脑的方法”是合理的；但价值分门、台账、回执页眉字段等一度扩散到普通任务路径（卡 57、卡 56、卡 64），把日常交付拖进高成本链路。

### 1.3 因此“该修什么”

| 诱人但次要 | 更本质 |
|---|---|
| 再加一个池节点类型 | 单一“现行入口”文档，消灭过时版本句 |
| 再扩拓扑节点 | 把验收断言变成可跑的契约测试 |
| 再加评分维度 | 按任务风险分层：日常直达 / 经验候选才进审查 |
| 再同步一份快照 | 明确哪些树只读、哪些可写、哪些禁止 Agent 改 |

## 2. 重新定义需求：症状 ≠ 原因，手段 ≠ 目标

### 2.1 用户真正想解决的底层需求

从拓扑原话与 10-30 裁决回读：

1. **可控**：高风险不绕过用户；经验进库必须用户点头。
2. **复利**：做法与踩坑能在以后任务里被找回来，且按真实复用计分。
3. **可换人**：后台不绑死某一家 CLI；审查与协作角色分开。
4. **可信**：配置、已安装入口、源码是同一套；回执可核对来源。

### 2.2 常见“问题定义”误区

| 表面问题 | 若当原因会怎么修 | 更可能的真实目标 |
|---|---|---|
| “DSH 验收又 FAIL 了” | 再开一轮热修卡 | 让规范与代码同批可测，减少轮次 |
| “普通任务缺价值分失败” | 给所有任务补评分 | 评分门只覆盖有审查来源的任务（卡 57 已证明） |
| “台账导致评分污染” | 继续补丁台账 | 台账纯旁路、不进结算谓词（卡 64） |
| “仓库里版本号乱” | 到处改字符串 | 运行根才是线上；仓库只标候选与快照 |
| “要不要再同步拓扑” | 再导出 JSON | 先问：代码是否已对齐最新用户意图 |

### 2.3 更值得先解决的问题（相对再加功能）

1. **现行入口一页纸**：打开仓库 30 秒内知道读哪五个文件、改哪一棵树、绝不能改哪几棵。  
2. **验收契约测试化**：把 Qoder/DSH 反复提的 P1～P3 类断言沉到 `unittest`（文档↔代码对齐检查）。  
3. **风险分层默认路径**：无经验日常任务默认不碰价值分/初审队列。  
4. **认知削峰**：拆或分区神文件前，先写特征测试锁住行为（PR #60 对 `store.py` 的判断成立）。

## 3. 二阶、三阶影响

### 3.1 若继续“加节点 / 加门 / 加卡”路径

| 阶 | 影响 |
|---|---|
| 一阶 | 某一验收 FAIL 被修好 |
| 二阶 | `SOURCE_MANIFEST`、拓扑、站点、入口 SKILL、OPERATIONS 四处要同步；漏一处→下一轮 FAIL |
| 三阶 | Agent 更依赖卡号上下文；新人与新会话更难；返工率上升；用户把时间花在验收而不是交付 |

证据：v1.6.10 热修两轮（#57/#58）；v1.6.12 四轮；v1.6.13 专门修“说明与代码对齐”。

### 3.2 若采用“权威收敛 + 契约测试 + 风险分层”

| 阶 | 影响 |
|---|---|
| 一阶 | 文档冲突下降；普通任务不再误入评分门 |
| 二阶 | 外部审查从“找文档矛盾”转向“找真实行为风险”；卡吞吐上升 |
| 三阶 | 拓扑可以变薄；`store.py` 才有安全拆分窗口；维护成本从“轮次税”转为“测试资产” |

### 3.3 对用户行为的副作用

- 门越多，宿主越倾向于“先绕过再补票”，或把本可直答的事塞进队列。  
- 评分与台账若曾影响结算，用户会不信任自动记分（卡 55/57/64 都是信任修复）。  
- 多轮验收成功会强化“再开一轮就能绿”的行为，掩盖缺 CI 的结构洞。

### 3.4 复杂度与维护

`development/` 约 230 个 `.py`，合计约 7.8 万行；神文件：`store.py` 3069、`retained.py` 2854、`cli.py` 2616、`memory.py` 1858、`orchestrator.py` 1556。  
继续在神文件上打补丁的边际成本高于新增小模块；但**无特征测试的拆分**会把隐含不变量打散到更多文件——PR #60 的保守判断正确。

## 4. 跨领域类比与更优解形态

| 领域 | 类比 | 可迁移的解 |
|---|---|---|
| 航空适航 | 设计意图 / 制造构型 / 在役构型必须可追溯且分离 | 意图（拓扑）、候选、发布、在役（运行根）四本账，禁止混改 |
| 临床实验 | 探索性使用 ≠ 注册试验 | 日常任务 ≠ 经验入库存证；分层协议 |
| SRE | 错误预算；变更与验证自动化 | 把“验收轮次”当错误预算消耗；契约测试=合成监控 |
| 知识管理 | 闪念 → 文献 → 永久笔记；不是每条闪念都进永久库 | 候选经验默认高门槛；检索命中 ≠ 仍正确 |
| 军事 ROE | 交战规则按威胁分级 | 高风险硬底线；日常宿主判断（已在 DECISIONS） |
| 编译器 | 类型检查在本地，不靠代码评审发现类型错误 | 文档-代码对齐断言应本地可跑 |

**最优解形态（建议，非本轮实现）**：

1. **薄控制面**：入口校验、租约、一次结算、事件链、用户裁决。  
2. **厚证据面**：回执、台账、评分旁路投影——可重建，不可反写控制谓词。  
3. **分层工作流**：L0 直答 → L1 交付归档 → L2 经验候选审查 → L3 隔离复验终审。默认走最低足够层。  
4. **单一现行地图**：仓库根 README 只指向“现行五件套”，历史树进 `archive/` 或明确 `FROZEN.md`。

## 5. 反方：假设“权威收敛+契约测试+分层”是错的

### 5.1 最强反对意见

1. **高仪式是有意的**：用户明确要双审、两轮验证、终审；简化=削弱主权。  
2. **拓扑即产品**：53 节点不是过度设计，是用户可编辑的规范 UI；“变薄”违反用户工作方式。  
3. **外部验收比单元测试更接近真实**：Qoder/DSH 读全貌，本地测试会过拟合补丁。  
4. **本机单用户系统**：没有团队 onboarding 成本；认知成本论证不成立。  
5. **PR #60 已证明最小修复优于大重构**：系统层方案是过度抽象。

### 5.2 反证与边界

| 反对 | 部分成立之处 | 不能推翻之处 |
|---|---|---|
| 高仪式有意 | 经验入库存证必须严 | 严规则被应用到无审查来源的普通任务时，是范围错误（#57），不是主权 |
| 拓扑即产品 | 用户原话优先正确 | 拓扑与代码/入口 SKILL 三方漂移时，产品变成“互相打架的说明书” |
| 外部验收更真 | 真机 CLI 行为本地难模拟 | 文档↔代码矛盾不需要真机；v1.6.13 两阻断就是对齐问题 |
| 单用户无 onboarding | 用户本人换会话也付认知税；卡号语言加剧 | — |
| 最小修复优先 | 对**已复现的单点洞**正确 | 对**反复同构返工**需要结构解，否则永远最小热修 |

### 5.3 重新评估后的方案

不采用“推倒重来 / 删拓扑 / 取消双审”。  
采用**兼容主权的收敛**：

1. 保留用户裁决与双审，但**默认路径分层**（已有意图，代码未处处落实）。  
2. 保留拓扑为意图源，但**仓库入口强制指向权威顺序**，过时句打戳。  
3. 保留外部验收，但**先跑对齐契约**，把轮次预算留给真行为。  
4. 大重构仍禁止，直到特征测试锁住神文件。

被放弃的选项：合并所有树到一个目录（破坏快照哈希）；取消价值分（用户已定线）；在 Linux 上为绿而改固定解释器（发版约束）。

### 7.2 命名与抽象问题

- **卡号驱动**：J10、卡 57、75A 出现在提交与测试名，函数名不承载规则 → 无卡上下文难搜。

- **目录日期当命名空间**：`architecture-package-20261027` 暗示冻结却含活动树。  
- **神文件职责**：`store.py` 同时像数据库、状态机、政策执行器。  
- **“候选/已上线”在节点上混写**：AGENT_READER 状态标签与问题/待办里的上线叙述交叉，需人工辨别。

5. **运行时卡顿**：v1.6.14 已加 events 索引；PR #60 证明监管分类非热路径。无生产 profiling，不臆造结算耗时结论。

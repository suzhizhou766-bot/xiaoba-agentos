## 2. 最新用户裁决：本地实现的准绳

### 2.1 审查参与方式

固定 DSH 一方，另一方为任意符合任务要求的开放 Agent，可以是外部 Agent，也可以是后台 Agent。早期“两个后台都不固定”方案已被这条裁决更新；冻结候选中的 AGY＋DSH、Qoder 固定备用也不能作为新模块的最终定义。

需要第二方审查时，以任务 ID 关联任务卡、原候选版本、当轮材料、参与者和回执。两方回执归集后提交裁决材料，保留分歧、FAIL、异常及旧历史。回执齐备不等于核验通过；待终审不等于用户已批准。

### 2.2 资源信息与日常调用

用户提供：哪个 Agent、在哪里（桌面端 / Web 端 / CLI 端及确切入口）、使用哪个模型。已有信息直接记录并绑定任务 ID；只补问调用必需而尚缺失的字段。

主入口按入口使用 computer use、Chrome 插件或终端正式调用。不要再进入对方 Agent 核实模型、读取设置确认用户说法、发探针或额外试调用。不要求每份回执重新登记用户已给出的来源信息或模型证明。可调用入口不代表工具必然可用；若本机缺少所需工具、权限或调用失败，应如实暂停汇报。

日常运行只有读取、调用和写入任务产物/记录。代码、配置、规范的修改放入明确的更新迭代。实际调用异常立即暂停，报告任务、Agent、端形态、入口、模型、失败步骤、实际错误及已完成内容；不自动重试、自修复或更换 Agent、模型、账号、上游。

调用故障与经验验证失败分开处理，网络/认证/工具异常不能自动消耗一次经验验证失败轮次。发布包的源码、配置和现场一致性预检属于软件发版门禁，仍须保留。

### 2.3 两轮经验核验

```text
新经验候选 → 用户初审通过 → 待隔离验证（第一轮）
  第一轮通过 → 自动进入待终审
  第一轮未通过 → 保留失败与评分 → 待重新验证（第二轮）
    第二轮通过 → 核对两轮差异并重点标明 → 自动进入待终审
    第二轮未通过 → 直接退役 → 监看展示 → 用户确认后手动删除
待终审 → 用户明确终审通过 → 发布检查与索引复验 → 正式经验
```

第二轮通过时重点显示“第二轮验证通过”、首轮未通过原因、采取的变化、两轮证据与评分差异、适用范围和残余限制。没有第三轮；不自动删除、不自动终审批准。正文或初审版本变化必须使不匹配证据失效，不能靠修改正文绕过失败记录与轮次限制；具体版本迁移规则需在实现时明确。

### 2.4 待验证索引与交付回流

初审有效的方法候选进入独立待验证索引，与正式长期记忆分开。后续相似真实任务检索、回读、核对适用条件并实际应用；仅召回或阅读不算使用。

用户说“交付”即接受明确任务和版本的成品。交付记录、踩坑、打法、偏好沿用原流程。本任务实际应用的旧经验附执行证据与任务评分回原卡，不重复建卡；只有当前轮次必要核验通过，才自动待终审。新经验仍先初审。引用、否定或讨论“交付”不触发验收；重复交付只结算一次。

真实任务证据如何接入现有隔离验证，必须同批改门禁并验证。不能以成品被接受推断其中每条经验都有效，也不能把回写材料当作隔离验证已经通过。

### 2.5 任务综合评分与快速择优

评分对象是每条任务整体表现，关联任务类型、目标、实际使用的经验、第二开放 Agent 与模型组合、质量、验证结果、耗时、返工、人工介入和可取得的成本。缺失数据如实标记，保留评分依据、量表和策略版本。

评分、检索索引与第二大脑长期记忆共同支持同类任务快速择优。小八用明确规则筛选和排序，主入口执行；不要求用户逐任务判断哪个 Agent 好、哪个模型快，也不恢复已退役的核心策略进化运行时。

量表、权重、合格线、冷启动与同分选择策略尚未最终确定，须形成可审核的配置契约。核验通过应由明确的当轮技术条件、执行证据和独立审查共同判定，不能只用总分或两份回执齐备代替。现有 DeterministicJudge 的回答排名分不是任务综合分。

### 2.6 统一架构与升级入口

监看中心 HTML 拓扑是模块规范修改、升级接续、版本源码记录和正式发版的统一用户入口：

```text
选择模块 → 编辑提案 → 待发布文件夹 → 授权 Agent 认领接续
→ 实施、功能验证、独立审查与构包 → 原生预检
→ 用户点击正式发版 → 实际切换与回读 → 版本记录
```

正式发版按钮承接原有命令行流程；最新用户裁决允许用户在页面确认执行，不再要求每次由用户手输切换命令。包校验、审查、现场检查与回读不能减少。第一次安装这个入口仍需本地部署任务完成，不能要求尚未安装的按钮先发布自身。

数据库为状态权威，文件夹供接续与审阅。已授权 Agent 先读 HANDOFF/ACCESS，再使用 `development/architecture-center/cli.py --workspace <同一工作区>` 的 JSON stdin 入口，读取、认领、续租、候选写入、记录检查点、登记包和完成交接。详见 [接续协议](../development/architecture-center/HANDOFF-PROTOCOL.md)。

跨模块改动需要明确每个模块的任务与最终合包范围。当前中心按单模块提案登记，不应把多卡批量合包、自动依赖升级或完整源码迁移当作已实现能力。目标正式包必须逐项包含候选改动，建立文件映射；规范和包外监看资产的安装位置要同批设计，不能登记一个未包含新模块的旧核心包。

正式包放入该任务 `artifacts/package/`，登记完整候选文件映射，交接完成并通过当前候选检查。用户在监看中心运行“正式包预检”，查看实际目标版本、变化清单和检查结果，再点击“正式发版”及具体确认。

原生预检有效期为 300 秒，切换时重查现场与包指纹；过期/变化后重新预检。它与经验两轮核验、模型确认及普通任务调用不是同一流程。

# 小八监看中心

一个只监听本机的页面：**运行总览**、**裁决中心**、**导演台**、**3D 导演台**、**Key 池**。地址 `http://127.0.0.1:8799/`。

## 开与关

- 开：双击 `启动监看中心.command`。它带看护启动监看中心并打开页面。
- 关：双击 `关闭监看中心.command`。看护进程、监看中心和它拉起的裁决后端一起停。
- 不开机自启。没开的时候不能裁决，待审队列也不会同步到第二大脑；重新开启后会补上。

## 结构

```
启动脚本 ──► 看护进程（--supervise）
                 └─► 监看中心（xiaoba_monitor.py，端口 8799）
                        ├─ system    页面、存活探针、各模块健康
                        ├─ overview  运行总览：只读读取 AgentOS 的数据库、日志、状态文件
                        ├─ review    裁决：拉起并看护裁决后端（内部端口），页面只和监看中心打交道
                        ├─ director  导演台页面（director.html）
                        ├─ localtools 导演台三个服务开关背后的控制器（127.0.0.1:8893）：拉起并看护
                        ├─ stage     3D 导演台：提供「小八3D导演台/dist」里的静态文件（/stage/）
                        └─ keypool   Key 池：拉起并看护 Key 池代理（127.0.0.1:8780）
```

- `monitor_core/web.py`：路由表和**统一的安全门禁**。每个地址声明一个门禁级别，默认拒绝；
  会改变状态的操作必须来自本监看页面，并带本次启动生成的令牌。
- `monitor_core/supervise.py`：进程看护。退出就按退避间隔重启；连续多次“起来没多久就退出”则熔断并报障，不无限重试。
- `monitor_core/modules/`：每个文件一个模块。
- `monitor.json`（可选）：覆盖端口、路径等默认值，默认值见 `monitor_core/config.py`。
- `logs/`：`monitor.log`（监看中心）、`supervisor.log`（看护）、`review-backend.log`（裁决后端输出）。按大小滚动。

裁决的全部逻辑——候选版本比对、证据哈希校验、调用已校验的 AgentOS CLI 写审核、发布、
把待审队列同步到第二大脑——仍然是小八 AgentOS 自带的
`小八AgentOS/integrations/review-center/server.py`，没有重写，它自己的来源与 csrf 校验也原样保留。
`monitor_core/review_backend.py` 负责把它作为监看中心的内部后端启动，只有两处不同：
写进第二大脑的链接指向监看中心（`http://127.0.0.1:8799/?candidate=…`），以及不再提供旧的独立网页。

- 后端只监听本机一个**每次启动临时分配的内部端口**，记录在 `run/review-backend.json`。旧的 `8797` 地址不再存在。
- 用哪份 AgentOS 配置：默认读取 Worker 的 LaunchAgent（`com.xiaoba.agentos.plist` 里的 `XIAOBA_CONFIG`），
  所以裁决与 Worker 始终是同一份配置。
- 原先由 launchd 常驻的 `com.xiaoba.review-center` 已停用（plist 改名为 `.disabled-20261005`）。
  恢复旧方式：把 plist 名字改回去，执行
  `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.xiaoba.review-center.plist`。
  监看中心发现旧服务在 8797 上运行时会改为使用它（并在健康状态里提示），不会同时再拉起一个。
- AgentOS 升级后如果 `server.py` 的启动步骤有变化，要对照检查 `review_backend.py` 的 `main()`。

## Key 池

把多个中转站的 API Key 合并成一个。页面上的「Key 池」标签从上到下是：指标卡、节点列表、实时拓扑（客户端 → 合并入口 → 各节点）、说明与设置区、安全检测、用量统计。

- 节点列表：每个节点一行，按中转站分组。行首的开关点一下立即启用或停用，不用保存；行尾「测试」直接在这一行显示连通结果，「设置」打开节点设置。组头的「全部启用」「全部停用」一次开关整个站，右上角可以只看启用或停用的节点。
- 节点设置：点节点名、「设置」或拓扑里的节点，从右侧滑出。启用开关在顶部，「删除」「查询余额」「测试连通」「保存」固定在底部；输入项分成基本信息、两路与模型、调度与兼容、余额查询、实时数据五组，可以折叠，展开状态记在浏览器里。按 Esc 或点抽屉外面关闭。
- 拓扑里拖动节点调整位置；「＋ 添加节点」接入新中转站（数量不限，最多 64 个）。

- 客户端里 API 地址填 `http://127.0.0.1:8780`（要求带 /v1 的填 `.../v1`），Key 填页面上复制的合并 Key。
- 代理是独立子进程 `monitor_core/keypool_proxy.py`，随监看中心启停；关掉监看中心后合并 Key 不能用。
- 调度：挑“当前并发 ÷ 权重”最小且不在冷却的节点；429 / 5xx 冷却 30 秒，401 / 403 冷却 5 分钟，连不上冷却 1 分钟，期间自动换别的节点。
- 节点与 Key 存在 `keypool.json`（权限 600，已在 `.gitignore`，不进版本历史）；页面只显示打码后的 Key。代理发现文件变了会自动重新加载。
- 日志：`logs/keypool.log`。端口可在 `monitor.json` 里用 `{"keypool": {"port": 8780}}` 覆盖。

### 调度与测速

- 调度：挑“当前并发 ÷ 权重”最小的节点；相同时挑最久没用过的，连续请求会轮流落到每个节点。
- 每个请求分开记录响应头、首字、总耗时；流式请求首字≈总耗时会标“整段返回”（中转站没真正流式，首字慢）。
- 按模型选路：监看中心给每个启用节点的每个 Key 读一次 `/v1/models`（启动时、改节点后、之后每 6 小时；失败保留上一份，5 分钟后再读），把清单写进 `keypool.json` 节点的 `models` / `payModels`。客户端要的模型，哪一路有就原样发给哪一路，没有它的线路不参与；清单还没读到的线路排在最后，原样发过去试。
- 缺模型时改用：节点编辑框里的「缺模型时改用」（`model` / `payModel`）只在整个 Key 池没有任何线路有客户端要的模型时才生效，这时分到这个节点的请求换成它再发出去。
- 模型别名：节点的 `aliases`（编辑框里每行一条「客户端要的模型名 = 这个节点上的模型名」）让名字不同的模型并进同一个并发池，例如 AMD 上 `Qwen3.8-Flash = Qwen3.8-Flash-Next`。发给这个节点时改名，最近请求和用量记录里会标出「要的是 A、实际发的是 B」。两边其实是不同模型时回答质量会随线路变化，要对比模型效果时把别名删掉。
- 对外公布的模型：客户端向 Key 池读 `/v1/models`（或 `/models`）时由代理自己回答，不再转给某一个节点。清单是 `keypool.json` 顶层的 `publishedModels`，在 Key 池页面右侧「对外公布的模型」里勾选；不设就公布所有启用线路的模型合集。公布清单只决定客户端看到什么，不拦请求。带 `X-KeyPool-Node` 的诊断请求仍按旧方式转给指定节点。
- 站点限速：同一个地址（域名加端口）下的节点算一个站。中转站按客户端 IP 限流时，限的是整个站而不是某个 Key，所以并发和间隔要整个站一起算。`keypool.json` 顶层的 `stations`（例如 `{"tierflow.cn": {"maxConcurrency": 2, "minIntervalSeconds": 3}}`）设置每个站同时最多几个请求、两次请求之间至少隔几秒，在 Key 池页面「站点限速」里改，0 表示不限。超出的请求先交给别的站，没有别的站能接就排队（最多 `queueTimeoutSeconds` 秒）。站内的节点仍然轮流使用。
- 对方按 IP 限流（429 且回复里有 `client ip` 之类的字样）：整个站暂停 `ipLimitPauseSeconds`（默认 15 秒，对方给了 Retry-After 就按它，最多 120 秒），节点不冷却、不计失败。这个请求先交给别的站；没有别的站能接就等暂停结束再发，客户端一般看不到这次 429。普通的 429（没有这些字样）仍按节点冷却、换下一个节点。
- 内容被中转站过滤（回复里有 `sensitive_words`、`content_filter`、`content_policy`）：是请求内容的问题，节点不冷却、不计失败，同一个站的其余节点直接跳过，换别的站；没有别的站就把对方的原话返回。
- 找出触发内容过滤的那段文字：在 `keypool.json` 的 `settings` 里加 `"captureRefused": true`，代理会把下一个被内容过滤拒绝的请求存到 `run/keypool-usage/refused-request.json`（权限 600，只存一份，请求里的密钥已打码）；然后运行 `/usr/bin/python3 tools/keypool_filter_probe.py`。脚本把请求拆成小段经 Key 池发回原来的节点，逐步缩到最短的触发内容；和正常请求共用站点限速，进度随时存盘，可以中途停掉再接着跑。查完删掉 `refused-request.json` 和 `refused-request.probe.json`，并去掉 `captureRefused`。
- 模型不支持时自动换线路：节点返回 404，或返回 400 且回复里提到 model，视为「这个节点没有这个模型」——不算节点故障、不冷却，直接换下一条线路重试，并在 10 分钟内不再把这个模型的请求分给它（`unsupportedModelSeconds`，改节点配置后立即清除）。所有线路都不支持时，把上游的错误原样返回。
- 双路（套餐 Key + 余额 Key）：同一个账号有两种结算的 Key 时，节点编辑框里两个都填（`key` 是套餐 Key，只有一个 Key 的节点也填它；`payKey` 是余额 Key）。默认先套餐后余额，可改。换路有两个依据：余额查询读到某一路剩余为 0 时直接走另一路；某一路被上游以 401 / 402 / 403 拒绝，或 429 且回复里写明是额度问题时，同一个节点立刻换另一路重发，客户端看不到错误，被拒的那一路停 5 分钟（`authFailCooldownSeconds`）再试。单纯的 429 仍按限流处理。两路都不行节点才冷却、换别的节点。余额底线（`payFloor`，元，可选）：按量余额降到这个数就不再走余额路；这是硬规则，10 分钟内读不到新的余额（`balanceHintSeconds`）也不走。为了让代理知道余额，双路或设了底线的节点在页面没开着时也每 60 秒查一次余额。「最近请求」和拓扑里会标出走的是哪一路。套餐用完时上游到底返回什么，还没有实际样本，识别规则是按常见写法定的。
- 用量统计：代理把每次尝试记一行到 `run/keypool-usage/usage-日期.jsonl`（权限 600，留 90 天，代理启动时清掉过期的），只有元数据——时间、节点、线路、实际模型与客户端要的模型、接口路径、状态、第几次尝试、响应头 / 首字 / 总耗时、输入 / 输出 / 缓存 token——不记请求和回复的内容，也不记任何 Key。token 数是转发时顺手从上游回复的 `usage` 字段读的（OpenAI 与 Anthropic 两种写法、流式与非流式都认；只留回复的开头 16 KB 和结尾，不改动转发内容），上游没给就记为未知而不是 0。Key 池页面底部的「用量统计」面板显示总请求数、成功率、token、平均耗时、模型 / 节点 / 接口分布、按小时或按天的趋势、可筛选分页的明细，并可导出 CSV（`/api/keypool/stats`、`/usage`、`/usage.csv`，逻辑在 `monitor_core/keypool_stats.py`）。花费是估算：余额读数每次变化记一行到 `balance.jsonl`，把每个节点“变少的部分”加起来，充值和续期不算；它不是逐笔账单，分不到单次请求，没填余额查询会话的节点没有。目录可用 `{"keypool": {"usage_dir": "…"}}` 改。
- 从现在起重新统计：用量统计里的这个按钮只记一个起算时间（`run/keypool-usage/baseline.json`），之后统计、明细和导出都只算这个时间以后的请求；记录文件不删，点「恢复全部」就回到完整数据。旁边的「重置筛选」只把筛选条件改回默认。
- 余额查询：节点的 API Key 查不了余额，要在节点编辑框里另外填站点网页登录后的 Session Cookie 值和 Session Token（TF-User）值（可选，两个都要填）。它们和 Key 一样只存在 `keypool.json`（权限 600），页面只知道填没填，只发往节点自己站点的 https 根地址，不跟随重定向。Key 池页面开着时每 3 秒在后台自动刷新一次（页面关掉或切到别的标签页就停），拓扑里每个节点右侧显示首字响应和余额，鼠标悬停分别看状态详情和余额详情；也可以点「立即查询」或节点里的「查询余额」手动查。为了不触发站点限流，自动刷新每轮只查按量余额，换算单位缓存 10 分钟、套餐缓存 60 秒；某个节点被限流或出错后先停 30 秒，期间继续显示上一次的数字并标出原因。结果只留在内存里。规则（2026-10-01 起）：总余额(元) = quota ÷ quota_per_unit + 生效且未到期套餐的 max(0, amount_total − amount_used) ÷ quota_per_unit，保留 4 位小数；quota_per_unit 取不到按 500000；套餐接口失败时只报按量部分并注明；基础 token 剩余只作参考、不折算金额。返回非 JSON 视为限流，自动重试一次。
- 客户端标识：Key 池自己发的请求（测试连通、读模型清单、测速工具，以及客户端没带标识时的转发）用 `xiaoba-keypool/2.0`，不用 Python 自带的 `Python-urllib`——后者会被一些中转站前面的防护直接拒绝（Cloudflare `error code: 1010`，表现为 403）。客户端带了自己的标识就原样转发。测试连通遇到这种拦截会提示「被对方站点的防护拦截」，与 Key 无关。
- 节点专用的客户端标识：节点编辑框里的「客户端标识」（`userAgent`）填了以后，发给这个节点的请求、测试连通和读模型清单都用它；留空则按上一条。
- 熔断（参考 cc switch 的做法）：偶发一次失败不停节点。连续失败 `breakerFailures` 次（默认 3），或最近 20 次里错误率达到 `breakerErrorRate`（默认 0.6，至少 `breakerMinRequests` = 10 次才看）才停，停多久仍按上面的冷却时长；冷却结束后只放一个请求试探，连续成功 `breakerSuccesses` 次（默认 2）才算恢复，试探失败立刻再停。双路节点两个 Key 都被拒时不攒次数，立刻停。想回到“失败一次就停”：在 `keypool.json` 的 `settings` 里写 `"breakerFailures": 1`。IP 限流、内容过滤、模型不支持不计入熔断。
- 超时分开设：`timeoutSeconds`（默认 300）是总的；流式请求可以另设等响应头的 `firstByteTimeoutSeconds` 和两段之间断流的 `streamIdleTimeoutSeconds`，默认 0 = 和 `timeoutSeconds` 一样。**不要照搬 cc switch 的 60 秒**：2026-10-08 统计本机用量记录，成功的流式请求响应头耗时中位数 6.6 秒，但 90% 分位是 135 秒、最长 267 秒，设成 60 秒会砍掉一成以上本来能成功的请求。
- 位置排布：节点只落在格位上（列从右往左、行从上往下），拖动时显示落点轮廓，松手吸附，格位上已有节点就对调；存的是 `slot`（第几列第几行），不随面板宽度变。
- 对比测速：`/usr/bin/python3 tools/keypool_speedtest.py --model <模型名>`（客户端用 /v1/messages 时加 `--api anthropic`）。直连与经 Key 池各发一个极短请求对比首字，Key 只从本机读取、不打印，消耗很少额度。

### 安全检测

中转站是你和模型之间的中间人，风险是看到你发的内容、以及篡改回复（往工具调用里塞危险操作让会执行命令的客户端自动跑）。安全检测在 Key 池里设一道关：

- 回复里的工具调用收齐后按模式匹配，命中高危（下载后执行、反弹 shell、读凭据外发、写开机自启、关防护、大范围删除、调用未声明的工具）直接拦截，普通文字照常实时输出；拦截后该节点自动隔离，看过后在页面「放行」。
- 请求发出前扫描密钥（私钥、各家 API Key、GitHub Token、.env、你自己的中转/合并 Key），自动打码后再发（可在页面改成只告警）。
- 页面「安全检测」面板显示检查/拦截/告警/打码次数、开关、被隔离的节点和安全事件；可整体开关。
- 规则抓不住藏在正常代码里的隐蔽后门，所以客户端仍要保持“执行前确认”、少放重要密钥、每个中转站只充少量余额。

## 导演台的本地工具开关

导演台里「图片 / 视频反推」「Real-ESRGAN 超分」「深度图转换」三个开关，点的是本地工具控制器（`AI视频管线/06_内部工具/local_tools_control_server.py`，端口 8893），由它启停三个服务。控制器由监看中心拉起并看护（`monitor_core/modules/localtools.py`），所以监看中心开着，开关就能用——重启机器后也一样，不需要再双击 `start_prompt_director_services.command`。

- 三个服务本身不随监看中心自动启动，开不开由开关决定。
- 监看中心关闭时，先关掉还开着的服务，再关闭控制器。
- 端口上已有一个控制器（比如那份启动脚本拉起的）时，监看中心会结束它并自己重新拉起；占着端口的不是控制器时不动它，在健康状态里报障。
- 开关显示「控制器离线」是控制器没起来（看 `logs/local-tools-control.log`）；显示「启动失败」是那个服务自己起不来，鼠标停在开关上能看到原因。
- 反推服务跟随 Antigravity 桌面端当前选中的模型（与 AgentOS 的 `local_agy` 路由用同一个读取器），所以用它时 Antigravity 要开着且只有一个窗口。
- 路径和端口可在 `monitor.json` 的 `localtools` 里覆盖，默认值见 `monitor_core/config.py`。

## 导演台 · 参考素材（角色卡 / 场景图）

`director.html` 末尾的「参考素材」脚本块（2026-10-07）把“我有角色卡和场景图”接进提示词导演台，目前只为 MiniMax H3 写了引用规则：

- 「参考素材」卡片：拖入或点选图片（最多 6 张），每张选一个身份（角色卡、场景参考、首帧、尾帧、构图基准），顺序就是 `<Picture N>` 的编号，也是 ComfyUI 里 `ref_image_0、1…` 的顺序。浏览器读不到文件路径，只能拖入或点选。图片只留在页面内存里，刷新后要重新加入；本地存储 `xiaoba.director.refs` 只记身份、文件名、小缩略图和文字描述。
- 人物栏第三个选项「用角色卡」：外观由图决定，年龄、身高、体型、服装那几个下拉框收起，只留表情、动作、视线。
- 「看图补全」：把图发给本机的反推服务 `POST http://127.0.0.1:8890/describe`（`AI视频管线/06_内部工具/prompt_reverse_server.py`），它调后台 AGY，固定用 Gemini 3.8 Flash (High)，返回每张图的英文定义、角色外观、场景描述和中文提醒，填进可编辑的输入框。一次约 1 到 2 分钟；要先在「本地工具服务」里点亮「图片 / 视频反推」。不走 Key 池。
- 「四步落地执行卡」：素材准备（哪张图接哪个输入）、效果预演、参数速查、完整 6 段式提示词，对应 `~/.gemini/config/skills/minimax-h3-video-director/SKILL.md` 的交付规范。
- 给别的模型适配：在脚本块的 `ADAPTERS` 里加一项（默认定义、`plan()` 产出素材行 / 主体行 / 留存行、`slot()` 输入名），并在那个模型的提示词函数里像 `minimaxH3Blocks()` 一样调用 `RefKit.plan(模型编号)`。

## 3D 导演台

「小八 3D 导演台」（三维摄影预演工作台，React + Three.js 的纯前端应用）的完整工程在本目录的 `小八3D导演台/`，2026-10-06 从 Codex 的临时输出目录迁入。监看中心只把它的构建产物 `小八3D导演台/dist/` 原样提供在 `http://127.0.0.1:8799/stage/`，页面里是「3D 导演台」标签，也可以点「单独窗口打开」。不起额外进程，不再需要原来的 5173 端口。

- 改了源码后：在 `小八3D导演台/` 里执行 `npm run build`（依赖已随目录带来，不需要联网），刷新页面即可。`npm test` 跑它自己的测试。
- 资源路径固定在 `/stage/` 下（`vite.config.ts` 的 `base`）。`dist/` 和 `node_modules/` 不进版本历史。
- 页面与监看中心同源，但内容安全策略只允许它加载和连接自己 `/stage/` 下的东西，连不了裁决、Key 池等接口。
- 本机工程库：从监看中心打开时，草稿自动保存到 `小八3D导演台/工程库/`（`/stage/api/…`，不进版本历史）。草稿是 `drafts/<编号>.json`；模型和图片按内容哈希存在 `assets/`，同一个素材只存一份，工程文件里只留引用，所以保存时只上传没传过的素材。删除草稿时顺带清掉不再被任何草稿引用的素材。读取只挡跨站，写入要求来自本机监看页面。浏览器里原有的草稿第一次打开时会搬过来一份（浏览器里的不删）。
- 送到提示词导演台：导演编译器里的「送到提示词导演台」把当前镜头换算成参数面板的取值（景别、焦距、光圈、机位高度与角度、运镜、灯光方向与光比、人数、目标模型），写进同源的本地存储 `xiaoba.stage.handoff`，并切到「导演台」标签；`director.html` 末尾的接收脚本用「反推回填」同一个入口填好，底部提示可一键撤回。不走网络。取值表在 `小八3D导演台/src/directorBridge.ts` 的 `DIRECTOR_CODES`，抄自 `director.html` 的下拉框——那边改了选项，这里和它的测试要跟着改。连续值取最近的档位；关键帧轨迹、角色外观不在面板里，仍以交接包为准。
- 用 Key 池模型写最终提示词：导演编译器里的同名按钮把所选视频模型的使用指南和纯净提示词发给 `POST /stage/api/compose`，后台用合并 Key 请求本机的 Key 池（`/v1/chat/completions`，非流式，最长等 240 秒），页面拿不到任何 Key。只在点按钮时发请求，会消耗额度；节点设了调用模型时由节点决定用哪个模型。它只代写提示词，不出图。
- 文件在每次请求时现找：在 `小八3D导演台/` 里 `npm run build` 之后刷新页面就是新版本，不需要重启监看中心。
- 需要较宽的画面（工作区至少约 1040px）。使用说明见 `小八3D导演台/README.md`。Tauri 桌面壳只是骨架，没有接入监看中心。

## 裁决中心里的“有文件等你核对”（2026-10-12 新增，需要 AgentOS v1.5.5 或更新）

经验发布失败时，小八把被换下来的原文件留在原处，不自动删除，等用户核对。以前只能在终端里用
`xiaoba memory-retained-list` 和 `xiaoba memory-retained-resolve` 处理，现在裁决中心顶部会出现一栏：

- 没有待核对的文件时，这一栏不显示。有的时候，标签页上的数字是“待审候选数 + 待核对文件数”。
- 每个文件一行：原来的文件名、为什么被留下、原位置、保留位置、时间和大小。
- 文件还在：按钮是“移到废纸篓”。文件已经不在了（用户自己删过）：按钮是“标记为我已删除”。
- 点按钮后要再点一次“确认”才执行；一次只处理一个，没有批量。命令行拒绝时，原因显示在这一行下面，文件仍留在清单里。
- 监看中心只是替用户调用已安装的小八入口：`GET /api/review/retained` 对应列出，`POST /api/review/retained/resolve` 对应处理。
  处理请求必须带页面令牌；路径必须是清单里此刻列着的那一个；文件的设备号和编号由服务端从清单里取出交给命令行核对，不经过页面。
- 每分钟读一次清单，点“刷新”立即重读。读不到清单时保持上一次显示的内容，不当成“没有文件”。
- 实现在 `monitor_core/modules/review.py` 的“待核对的保留文件”一段和页面里的 `rcKept` 一段；测试在 `tests/test_monitor.py` 的 `ReviewTests`。

## 裁决中心里的“冻结任务”（2026-10-14 新增）

任务在一侧后台失败时会被冻结，成功那一侧的输出与执行回执原样保留。冻结的任务不会自己恢复，以前只能在终端里用
`xiaoba task-resume 任务编号 --freeze-hash 冻结哈希` 恢复，现在裁决中心顶部有一栏“冻结任务”：

- 没有冻结任务时显示“现在没有冻结任务。”。有的时候，标签页上的数字是“待审候选数 + 待核对文件数 + 冻结任务数”。
- 每个任务一行：标题、任务编号、冻结时间、失败的是哪一侧与原因、失败类型、成功侧是否有执行回执、冻结哈希，
  以及失败侧现在有没有新鲜的合格探测（没有的话恢复会被拒绝，要先重新“上班”探测）。
- 点“恢复”后弹出确认框，显示任务编号和冻结哈希，写明只补跑失败侧；确认后才执行。一次只恢复一个，没有批量，不自动重试。
- 结果原样显示：成功、证据缺口、需要先重新探测、冻结哈希不一致等，中文说明下面附命令行返回的原文。
  单轮输出预算耗尽的任务，命令行会恢复并附带拆分提醒；列表和确认框里会提前提示“建议拆小后重新提交”。
- 监看中心只是替用户调用已安装的小八入口，配置与 Worker 相同，不读写数据库：`GET /api/review/frozen` 对应
  `xiaoba status --json`（筛出 `frozen_paused` 与遗留的 `resume_ready`），`POST /api/review/frozen/resume` 对应 `task-resume`。
  恢复请求必须带页面令牌；任务必须是清单里此刻冻结着的那一个，哈希必须与此刻的记录一致。哈希、回执与健康的复核由命令行完成。
- 进入裁决中心时读一次清单，之后每 30 秒读一次。读不到清单时保持上一次显示的内容，不当成“没有冻结任务”。
- 实现在 `monitor_core/modules/frozen.py` 和页面里的 `rcFrozen` 一段；测试在 `tests/test_frozen.py`。

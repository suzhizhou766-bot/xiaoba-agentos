# 第 2 步框架与边界：固定切换命令、发布分档、分块验收

日期：2026-10-11。写给主力（GPT）。起草：Claude Code（小克），只给方向和边界，不参与实施。
前提：第 1 步已随 v1.5.3 上线。总边界仍以 `给主力的框架与边界.md` 的五条“不许动的”为准，这里只补第 2 步特有的。

## 为什么这一步最要紧

v1.5.3 切换时，手写的切换脚本报告 Worker 已恢复，实际旧进程还在跑旧代码：停服务的命令参数写错，又没检查命令是否成功。这是第五份手写脚本，也是第一次在上线时真出错。它是主力独立读回才发现的，不是脚本自己发现的。第 2 步要消除的就是这一类问题。

## 拆成两版（用户 2026-10-11 同意）

- 第 2 步甲：固定切换命令，加上第 1 步留下的几项补丁（见“顺带要做的”）。
- 第 2 步乙：发布分档和分块验收。

理由：切换命令是高风险的一块，单独发一版，出问题好定位；分档和分块验收改的是验收流程本身，和它没有代码上的牵连。主力认为合成一版更好，可以和用户说。

## 一、固定切换命令

### 必须做到的
1. 命令在发布包里，和其它代码一样有测试、过验收。命令本身不含任何版本号。
2. 三种用法：只看计划、只读预检、正式执行。前两种不写任何东西。另外提供一条随时可跑的“读回”，只读。
3. 成不成功看实际状态，不看步骤是否跑完。正式执行结束前必须亲自读回并全部满足，才能报告成功：
   - 旧 Worker 进程已经退出，新进程的编号不同；
   - 运行状态文件里的代码指纹、清单指纹与磁盘一致；
   - 两处已安装入口的发布校验都通过，指向新版本；
   - 自检通过。
   任何一项不满足，报告失败并说明是哪一项，不得报告成功。
4. 每一条外部命令都检查返回码。启停服务之后要等待并确认进程真的停了、真的起了，“服务已登记”不算。
5. 中途失败要退回到切换前的状态，并明确报告“已退回”或“退回失败，需要人工处理”，两者不能混。（Kubernetes 的发布也是这个思路：以探针读到的实际就绪状态为准；超时只标记为失败，不替人悄悄处理。）
6. 某一版特有的动作（改配置字段、装新模块、迁移数据）写成带编号的小步骤，随发布包声明，每步有检查、执行、撤销三部分。固定命令只负责按顺序跑它们。已经随某一版上线执行过的步骤不得再改，每步记下内容哈希，被改动时预检失败；要纠正就加新的步骤。（数据库迁移工具 Flyway 的做法：已执行的迁移带校验和，改了就校验失败。）
7. 正式执行前拒绝的情况：队列里有未完成的任务或未释放的租约；预检结果过期；预检之后现场指纹变了。
8. 测试要覆盖：每一步失败后的退回；这次的 Worker 假恢复（旧进程没退却报成功）必须有一项回归测试。

### 不许做的
- 不新建备份文件或备份目录。退回靠执行过程中记下的原内容，结束后不留副本。
- 不由 Agent 执行正式切换。正式执行由用户在自己的终端运行。
- 不碰认证、登录材料、模型和线路选择。
- 在第 3 步之前，对第二大脑的写入范围不得比 v1.5.3 的切换更大。

### 第一次用它上线怎么办
包含这条命令的那一版，本身就要用这条命令来切换（从已验证的发布包里运行），不再手写脚本。这是新代码第一次碰线上，所以验收时要多一样证据：在一份复制出来的现场上完整演练一遍，包括故意让某一步失败、确认能退回。演练记录进验收材料。

## 二、发布分档

### 档位由工具算，不由 Agent 判断
工具比较上一版和候选的文件清单，按改动的路径给出档位和理由：

| 档 | 条件 | 要过的关 |
|---|---|---|
| 补丁 | 只改了文档，或只改了不带底线标记的测试 | 全部测试通过、自检通过、只读预检通过。不过两个后台 |
| 常规 | 改了运行代码、脚本、配置、服务模板、入口技能卡、任一技能；或改动、删除了带底线标记的测试；或改了标记清单本身 | 两个后台审查。技能只审改动的那个 |
| 迁移 | 数据库结构版本变了；带有迁移步骤；目录结构或数据格式变了 | 现在的全套 |

### 边界
- 认不出归属的路径，一律往高一档算。
- 档位只能被人调高，不能被 Agent 调低。
- 三档都仍然是不可变发布，都由用户执行切换。补丁档省掉的只是两个后台的审查。
- 分档工具自己的规则文件被改动，按常规档。
- 验收记录里写明这一版是哪一档、工具给出的理由是什么。

## 三、分块验收

### 要解决的问题
候选改一个字，所有审查重跑。v1.5.1 跑了三轮，v1.5.3 跑到第八轮。

### 做法
- 把发布包的文件按固定的划分分成若干块，每块有自己的哈希。划分随包声明，轻易不变。
- 一份审查结论绑定四样：块的哈希、审查的后台、审查用的说明文字的哈希、结论。
- 候选修改后，只有哈希变了的块需要重审；没变的块沿用同一版里上一轮的结论。

### 边界（2026-10-11 按用户意见，参考成熟框架的做法后改写）
参考了三类现成做法（出处见文末）：
- GitHub 的评审：批准绑定的是评审者当时看到的那份改动；改动的内容变了，批准自动作废，包括基线变了的情况。不是按时间或版本作废。
- Bazel 的构建缓存：结果能不能复用，看一个由全部输入算出的键：源文件、命令、环境、工具本身都算在内。键相同就复用，跨多少次构建都行。出问题几乎都是因为有输入没被算进键里，而不是哈希本身不可靠；键算漏时留下的旧结果还会一直被误用，需要清掉。
- Gerrit 的评审：新版本提交后，旧的打分是否带过来由明确写下的条件决定（例如只是换了基线、代码没变）。

共同点：能不能沿用不看版本号，看“结论所依赖的东西是否全都没变”。所以原先“只在同一版本内沿用”的提法换成下面的规则：

- 一份审查结论的键由五样组成：这一块的内容哈希；它依赖的各块的内容哈希；审查说明的哈希；两个后台的组合；底线清单与标记清单的哈希。五样全部相同才可沿用，同一版本内和跨版本都按这一条。
- “依赖哪些块”由工具从代码的引用关系算出来，不靠人手写。算不出来的，按依赖全部处理。这是对应 Bazel 的教训：漏算依赖是这类机制最常见的出错方式。
- 每一轮都必须重审“改动总览”这一块，它不沿用。
- 迁移档的发布一律全部重审，不沿用任何旧结论。这相当于定期清一次旧结论，防止早先键算漏时留下的结论一直被沿用。
- 验收记录里逐块写明：本轮新审，还是沿用了哪一次任务的结论，以及当时的键。
- 两个后台各自独立给出结论、任何一方不通过即不通过，这条不变。

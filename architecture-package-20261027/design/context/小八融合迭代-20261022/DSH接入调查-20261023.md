范围：今晚 DSH 两次“连续 300 秒无进展”、第 38 轮门禁前探针“进程或端点未启动”、用户手动测试看到的“没有 API 模型配置可用”，以及“DSH 每次调用读取桌面端当前模型”这条硬要求。

做法：只读。读了 v1.6.5 候选代码、两轮隔离验收库、Key 池用量记录（只有元数据：时间、节点、要的模型、实际发的模型、首包时间、总耗时、token 数，不含内容和密钥）、DSH 桌面配置的结构（用 DSH 自带的 YAML 解析器，只输出条目 id 和模型相关字段，像密钥、地址的键一律打码；读之前问过守卫，允许读）。没有改任何代码、设置或 DSH 配置。

## 1. 结论先说

1. **“每次调用读取桌面端当前模型”现在已经做到了**，v1.6.4 线上和 v1.6.5 候选都是：`DshAdapter.run()` 每次先调 `_model()`，经 `gateway.local_cli_route` 跑 `scripts/dsh_desktop_route.cjs`，读 `~/.dsh/profiles/desktop/cordis.patch.yml` 里 `agent-default-model` 的 provider 和 model，再用 `dsh --profile headless --patch <这份桌面配置> --json` 调用。
   - 证据：桌面端当前选的是 provider `xiaoba`（显示名“小八并发”）、model `DeepSeek-V4.1-Flash`、思考强度 max；Key 池记录里今晚每一条 DSH 请求的 `asked`（DSH 要的模型）都是 `DeepSeek-V4.1-Flash`，健康记录里的模型也是它。两边一致。
2. **今晚卡住的根因不在“模型没对上”，而在 Key 池后面的上游节点**。“小八并发”就是本机 Key 池（127.0.0.1:8780，随监看中心启停）。Key 池把 DSH 要的 `DeepSeek-V4.1-Flash` 轮流发给不同节点：
   - 节点 `16760796526` 不认这个模型名，每次 404；
   - “积分服务”节点改成小写 `deepseek-v4.1-flash` 发出；
   - 另外 5 个节点**实际发的是 `tierflow_pro`**，也就是另一个模型。今晚 DSH 的审查大部分是 `tierflow_pro` 答的，不是桌面选的 `DeepSeek-V4.1-Flash`。这是 Key 池的节点映射（用户自己的设置），小八这边看不到也不该改。
3. **三次卡住都是上游节点接了连接却一直不发第一个字节**：

   | 时间 | 对应 | Key 池记录 |
   |---|---|---|
   | 20:16:37 | 第38轮 cli_background 第3部分（20:11:01 开始） | 积分服务，200 但首包为空，总 333970ms |
   | 20:23:42 | 第38轮 cli_background 第9部分（20:18:04 开始） | 积分服务，首包为空，总 336413ms |
   | 22:57:27 / 22:57:31 | 第39轮 cli_background 第1、3部分（22:52:18 开始） | 积分服务、tierflow_pro 节点 17022244458，首包都为空，约 308–312 秒 |

   300 秒无进展规则这三次判得**没错**：上游确实一个字都没回。Key 池对“连上了但不出首包”没有超时，会一直等到小八这边 300 秒后断开。
4. **另一个隐患：DSH headless 生成期间不发任何进度**。正常完成的长审查，Key 池那边首包 1–3 秒就到了，上游一直在流式输出，但 DSH `--json` 只在整步生成完才提交一行，小八这边全程只看到开头 268 字节，阶段停在 `cli_ready`。最长一份 285.9 秒、47280 个输出 token（第38轮第7部分），离 300 秒只差 14 秒，再长一点就会被误判卡住。`dsh --profile headless --help` 只有 `--json`、`--session-id` 两个选项，没有逐段输出。
5. **第38轮门禁前那次“进程或端点未启动”**（22:29:55）：那段时间 Key 池**没有任何 DSH 请求**（20:26 到 22:38 之间一条都没有），说明探针根本没走到 Key 池，是 DSH 本机这一侧卡住。同一晚 `~/.dsh/profiles/desktop/` 下的 `node_modules`、插件管理目录在 21:09 更新过（像是 DSH 升级或重装插件），`cordis.patch.yml` 在 22:38 被改过，22:38:42 起 DSH 请求又出现了，和用户说“DSH 好了”对得上。探针把一切 `dsh timeout` 都归成“进程或端点未启动”，这个说法太笼统。
6. **“没有 API 模型配置可用”**：在 DSH 的 CLI 安装目录和桌面配置目录里没搜到这句原文，桌面端安装包是打包的，没解开看，所以出处**没核实**。按现在的配置（agent-default-model 指向 xiaoba / DeepSeek-V4.1-Flash，且这个模型在 xiaoba 的模型目录里），headless 调用能正常走到 Key 池（23:31、23:42 都有成功记录）。如果是在 21:09 到 22:38 之间看到的，很可能就是那段 DSH 本机配置坏掉的表现。
7. 健康探针只发一句“回复健康标记”的短请求，超时 300 秒。它能发现“DSH 本机起不来”，但发现不了“某个上游节点对大请求不出首包”（短请求会被 Key 池轮到正常节点），也发现不了“实际答题的模型被换成 tierflow_pro”。
8. 另：今晚 23:41 起机器上有一个不是我起的 `/tmp/dsh-probe/drive4.py` 在驱动 DeepSeek Harness 桌面程序，可能是别的会话在测 DSH，我没碰它。

## 2. 方案比较（都满足“每次读桌面端当前模型”）

| | A. 保留现接法，补强 | B. 换调用方式：小八直接按桌面端的 provider 配置调 OpenAI 兼容接口 | C. 保留现接法 + 在 Key 池加“首包超时换节点” |
|---|---|---|---|
| 做什么 | 读桌面配置后核对 model 确实在该 provider 的模型目录里，不在就立即判失败并给中文提示（“DSH 桌面端选的模型 X 不在提供方 Y 的模型列表里，请在桌面端重新选择”）；DSH 退出时 stderr 里出现“无可用模型配置”类字样立即判永久失败；探针用同一套检查，分开报“桌面配置读不到/模型不在目录/本机起不来/上游无响应” | 只用 DSH 桌面配置当“模型来源”，请求由小八自己发，能拿到逐字流式进度和首包时间 | Key 池对流式请求加首包超时（比如 60–90 秒），超时就换下一个节点重试；不碰 AgentOS |
| 解决哪个问题 | 模型读不到/配错时不再白等，提示清楚；探针分类更准 | 进度信号、首包检测都有了 | 今晚三次卡住的直接原因（节点不出首包） |
| 不解决 | 上游节点不出首包；DSH 不发进度 | — | DSH 不发进度（长生成仍可能逼近 300 秒） |
| 稳定性依据 | 本地文件校验，确定性高 | 少一层 DSH，但要自己处理鉴权 | 首包超时是代理的常规做法；今晚卡住的请求首包全为空，正常请求首包 1–43 秒 |
| 凭据 | 不碰 | **要读桌面配置里的 baseUrl 和 apiKey 才能直接调**，违反“不碰凭据”；除非用户另给一条无需密钥的本机接口。所以**不推荐** | 不碰（Key 池自己管密钥，小八不读） |
| 改动量 | 小：`dsh_desktop_route.cjs`、`adapters.py`、`recovery.py` 各几十行，加测试 | 大：新适配器、鉴权、流式解析 | 小：监看中心 `monitor_core/keypool_proxy.py` 一处，加测试 |
| 对 v1.6.5 | 改了运行代码，要重冻；打开增量开关后，估计要重审 model_source、standby_adapter_code、standby_probe_gate、cli_background 里受影响的几份和发布说明相关份，约 30–45 份 | 不适合放 v1.6.5 | **不影响 v1.6.5**：Key 池是监看中心的工具，不在发布包里，不需要双审重冻；按监看中心规则改并补测试即可，改前要用户同意 |

关于“模型被 Key 池换成 tierflow_pro”：这是 Key 池节点映射，A、C 都不改它。要让答题的就是桌面选的 `DeepSeek-V4.1-Flash`，需要用户在 Key 池里调整那几个节点的模型映射，或者在桌面端改选别的模型。小八只能报告，不能替用户改。

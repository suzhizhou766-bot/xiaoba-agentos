## 2. 改造方案：后台 Agent 插件

目标：**核心（调度、门禁、事件链、补位规则）稳定不动；每个后台是一份插件。** 新增或替换插件只审这份插件，核心不发版。

### 2.1 插件长什么样

每个插件一个目录，例如 `私人助理/插件/后台/<插件名>/`（位置待用户定），包含：

```
manifest.json      插件清单（下面字段）
adapter.py         适配器入口：只实现 run(prompt, context) -> AgentResult 和 readiness()
model_source.py    模型来源：每次调用前读一次，返回 {provider, model, model_source}；读不到就抛明确错误
probe.py           （可选）健康探针的特殊判定；没有就用核心的通用探针
tests/             插件自带测试
```

`manifest.json` 字段（草案）：
- `id`、`display_name`、`version`；
- `entry`：适配器入口；`model_source`：模型来源入口；`probe`：探针入口（可选）；
- `capabilities`：能力声明，例如只读审查、需不需要联网、是否流式、能否给进度信号；
- `requires`：依赖的本机命令或文件，用于就绪检查，只写路径，不写凭据；
- `env_scrub`：要从子进程环境里清掉的变量前缀；
- `failure_map`：这个后台特有的错误文字，对应到核心的故障类别（外部上游、外部认证、内部、进程不可用、模型不可用）；
- `defaults`：建议超时、无进展窗口（例如 DSH 可以单独声明长一些）；
- `sha256`：插件文件指纹，由审查流程填写。

### 2.2 核心怎么按清单工作
- 配置里的 `agents[]` 不再写 `driver`，改写 `plugin: <插件 id>`。核心按清单加载适配器，**不再有驱动白名单和逐个 if**。
- 谁是主审、谁是备用、几份才算数，**只看配置**（用户在配置里改，核心不发版）。门禁和切换不再写死名字，改成核对“验收证据里的成功后台 == 当时配置里启用的主审集合”，并核对每个插件的指纹在已批准清单里。
- 补位规则（探针真实失败才补、一个任务最多补一次、备用不算第二票）留在核心，按“主审/备用”角色判断，不按名字。
- 故障分类：核心保留通用规则，插件用 `failure_map` 补充自己的错误文字。
- 健康探针：核心发同一句健康请求；插件可以补一个本地预检（例如 DSH 先检查桌面配置读得到、模型在提供方的模型列表里，读不到立即失败、给中文提示，不等 300 秒）。

### 2.3 新插件怎么上线（只审插件本身）
- 跟现在技能登记同一个思路：草稿目录 → 生成插件审查说明（清单、全部文件、指纹）→ 两个后台审 → 发布到插件目录、登记指纹 → 用户在裁决中心确认启用。
- 核心发版只在改核心代码时才需要。插件的增删改走插件流程，题面只包含这个插件，几份到十几份，不是一百多份。
- 在用户确认启用之前，新插件只能当备用或不启用，不能直接顶替主审。

## 5. 并入：后台并发（2026-10-24，用户选“先甲，乙放 v1.6.6”）

调查见 `后台并发调查-20261024.md`。甲（发版审查脚本按后台分别设上限）已做，不在发布包。乙并入本方案：

- 插件清单加 `max_concurrent_runs`（进程级上限，默认 1），由配置给值，不写死。
- Worker 可同时领多份任务（`worker.max_parallel_tasks`），实际并发取在岗后台上限的最小值（主后台坏了换备用时按备用的上限算），与审查脚本的规则一致。
- 会话内子代理是插件的可选能力 `subagents: {enabled, max_active, max_depth}`，默认关；审查任务一律关（DSH 调用里加覆盖层 `maxDepth: 0`，不改桌面设置；Qoder 本来就关工具）。
- 测试：上限生效；排队不丢任务；多任务并发下租约、补位、事件链仍只结算一次（B20）。

# 后台并发调查（2026-10-24，Claude Code，只读）

用户问：DSH 有并发任务功能，Qoder 应该也有，AGY 不确定；能不能让它们执行任务时都用并发模式加快速度。本文只做调查和方案，没改任何东西，等用户定。

## 一、三个后台各自支持什么（依据：本机 --help 和安装包自带文档）

先分清两种“并发”：

- **进程级并发**：小八同时开几个 CLI 进程，每个进程审一份。三个 CLI 都支持，没有官方上限开关，由调用方控制。
- **会话内并发（子代理）**：一个 CLI 会话里，模型自己决定把活拆给几个子代理同时做。这是用户说的“并发任务功能”。

| 后台 | 会话内子代理 | 官方开关 / 依据 | 小八现在的调用方式 |
|---|---|---|---|
| DSH | **有**。`dsh-subagent` + `dsh-tool-subagent`（spawn / fork 两种），另有实验性 `agent-team`（队友收件箱 + 共享任务板） | `maxActiveSubagents`：每棵调用树同时在线的子代理数，默认 8；`maxDepth`：委派深度，默认 1（只允许直接子代理），0 为禁止。在桌面端“插件 → 子智能体”页面改，或写进 profile 的 patch。依据：`DeepSeek Harness/current/node_modules/@deepseek-ai/dsh-subagent/README.zh.md` 第 49–57 行，`dsh-tool-subagent/README.zh.md` 第 63 行 | 每份一个 `dsh --profile headless --patch <桌面配置> --json -` 进程。`--dump-config` 显示 headless 档案**已挂载**子代理工具，所以模型现在就可能自行委派，只是我们没要求、也没观察 |
| Qoder | **有**。内置 agent：Explore、general-purpose、Plan 等，用户目录里还有 3 个示例；`--agents <json>` 可临时定义 | 没有“并发数”开关；子代理要靠工具调用来启动。依据：`qodercli --help`、`qodercli agents list` | 每份一个 `qodercli -p … --tools "" --no-session-persistence --strict-mcp-config` 进程。**工具全关**（备用策略规定），所以子代理在小八里用不了 |
| AGY | **看不到**。`agy --help` 只有 `--agent`（选一个 agent）、`--mode`、`--sandbox`；`agy agents` 列表为空；没有并发或子代理参数 | 依据：`agy --help`、`agy agents` | 每份一个 `agy --mode plan --sandbox --input-format stream-json …` 进程 |

**结论**：三个后台都能靠“多开进程”提速；只有 DSH、Qoder 有会话内子代理，而且 Qoder 在小八里因为工具全关、用不上。AGY 没有找到会话内并发的官方开关。

## 二、小八现在的并发度

- **线上 Worker（v1.6.4 / v1.6.5 同）**：一次只领一份任务；同一份任务里 AGY、DSH 两个审查者同时跑（`worker.parallelism=2`，`orchestrator.py` 第 940 行用线程池）。所以线上最多同时 2 个 CLI 进程。
- **发版审查脚本**：`work/run_reviews_parallel.py 3`，3 个 Worker 同时各领一份，每份两个审查者 → 最多同时 6 个 CLI 进程（3 个 DSH、3 个 AGY，补位时有 Qoder）。参数就是命令行里那个 `3`，不在发布包里。
- **实测耗时**（第 41 轮）：DSH 每份 85–286 秒，AGY 53–118 秒，DSH 是慢的一侧；20 份、3 并行约 25 分钟。

## 三、开并发的影响

1. **双审独立性**：进程级并发不影响，每份仍是两个不同后台各自独立给结论。会话内子代理不破坏“两个不同后台”，但一份结论由几个子代理拼成：同一后台内部出现“自己审自己”的协作；子代理的部分输出、工具调用痕迹也更容易混进正文，撞上 B19 输出卫生（空输出、工具调用标记、推理外露都判失败）。这类失败几乎是 DSH 发不出版的主要原因。
2. **门禁与证据**：门禁按“每份一个任务、每个审查者一次运行”核对证据。子代理的内部运行不进小八的事件链，补位规则也没有为它设计。
3. **Key 池 / 节点压力**：DSH 走 Key 池 `127.0.0.1:8780`（provider“小八并发”）。会话内子代理是在一份审查里再乘以 N 倍请求；进程级并发是线性增加。已知 tierflow 站点每个 IP 约每分钟 10 次请求，所有账号共享（超了就 429），Key 池给 tierflow 设的是 2 并发、7 秒间隔；节点 `16760796526` 对 DeepSeek-V4.1-Flash 每次 404。第 41 轮门禁前 DSH 报的“PI_AI_ERROR: Unexpected message role”是否和负载有关，没核实。
4. **Qoder 当日额度**：额度按用量算，并发不省额度，只是更快用完（10-23 就用完过）。Qoder 是备用，开高并发会让它在主审出故障、真正需要补位时已经没额度。
5. **AGY**：Antigravity 有自己的服务端限流（第 42 轮第一次探针遇到过 500）；多开进程会更容易撞上。

## 四、方案（按插件化原则：每个后台插件自带可配置的并发参数，不写死）

**甲、只改审查脚本 / 监看中心（不在发布包里，现在就能做）**
- `run_reviews_parallel.py` 现在只有一个全局 `WORKERS`。改成每个后台一个上限，例如 `{"dsh_review": 3, "agy_review": 4, "qoder_review": 1}`，从工作区里的配置文件读；某个后台到上限时，新任务排队，不挤占别的后台。
- 监看中心 Key 池页显示当前并发和 429 / 404 计数，便于定上限。
- 不动会话内子代理（保持现状，不在题面里要求委派）。
- 风险最小；只影响发版审查的速度，不影响线上任务。

**乙、需改 AgentOS 运行代码（走发版流程，建议并入 v1.6.6 插件化）**
- 每个后台插件声明 `max_concurrent_runs`（进程级上限，默认 1），Worker 能同时领多份任务（`worker.max_parallel_tasks`），总并发由各插件上限共同约束；这一点和“后台 Agent 插件化方案-20261023”合在一起做。
- 会话内子代理作为插件的可选能力 `subagents: {enabled, max_active, max_depth}`，默认关闭；只对需要工具、且用户明确允许的单 Agent 日常任务开，**审查任务一律关**（理由见第三节第 1、2 点）。DSH 关的办法是 patch 里设 `maxDepth: 0`，Qoder 已经是工具全关。
- 需要的测试：上限生效、排队不丢任务、租约 / 补位 / 事件链在多任务并发下仍只结算一次（B20）。

**建议**：先做甲（每后台上限，DSH 3、AGY 4、Qoder 1，跑一轮看 429 / 500 的情况再调），乙放 v1.6.6 和插件化一起发；审查任务不开会话内子代理。DSH headless 现在挂着子代理工具，是否要在审查调用里显式关掉（`maxDepth: 0`），也放 v1.6.6 一并定。

## 五、需要用户定

1. 做不做甲；如果做，各后台的上限取多少。
2. 乙是否并入 v1.6.6 插件化方案。
3. 审查任务里是否明确禁用 DSH 子代理（现在默认可用、未观察到实际使用）。

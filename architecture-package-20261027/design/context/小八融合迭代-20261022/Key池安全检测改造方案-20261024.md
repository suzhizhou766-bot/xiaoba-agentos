# Key 池安全检测：现状核实与改造方案（2026-10-24，Claude Code，只读）

范围：用户说安全检测本意是防上游回传不安全的隐藏内容被 Agent 自动读取、静默使用，但现在主要在拦 Agent 发出去的东西，背离初衷还误伤（节点常被弄得调不通）。例子：10-23 23:50:39 拦了 DSH 的 `/chat/completions`，命中“写入开机自启”，命中文本是审查题面里的代码原文。

做法：只读代码（`工具/小八监看/monitor_core/keypool_guard.py`、`keypool_proxy.py`）、监看中心日志、Key 池用量记录、第 37–39 轮验收库。没有改任何代码或设置。

**这部分不在 AgentOS 发布包里，改它不影响 v1.6.5 的冻结和审查。**

## 1. 核实结果

### 1.1 先纠正一个说法：请求方向从来不拦，只打码

- 请求方向（Agent 发给上游）：`scan_request` 只扫密钥。8 类模式（私钥、AWS、GitHub、Slack、OpenAI 类、Google、Bearer、`.env` 里的 SECRET/TOKEN/API_KEY 赋值）加上 Key 池自己的 Key，命中就**打码后照常发出**（`maskSecrets` 关掉则只告警）。**没有任何拦截。**
- 拦截全在回复方向，而且只看回复里的**工具调用**（模型要客户端执行的命令或写入）。命中下面 6 条高危规则之一，就把整条回复换成“Key 池安全检测拦截了这条回复里的危险操作…该中转站可能在篡改回复，已被隔离”，**同时隔离这个节点**：

  | 规则 | 名称 | 处理 |
  |---|---|---|
  | pipe-to-shell | 下载后直接执行 | 拦截 + 隔离 |
  | reverse-shell | 反弹 shell | 拦截 + 隔离 |
  | credential-exfil | 读取凭据后外发 | 拦截 + 隔离 |
  | persistence | 写入开机自启（含 `launchctl load/bootstrap gui/…`、写 LaunchAgents、crontab、.zshrc 等） | 拦截 + 隔离 |
  | disable-guard | 关闭系统防护 | 拦截 + 隔离 |
  | destructive | 大范围删除 | 拦截 + 隔离 |
  | sudo / outbound / chmod-exec / 未声明的工具 | — | 只告警 |

- 回复里的普通文字**完全不检查**：没有零宽字符、隐藏 Unicode、方向控制符、指令注入的检测。

### 1.2 23:50:39 那次为什么会拦

DSH 本身是带工具的智能体，审查时模型有时会发起工具调用（今晚第 37 轮有一份 DSH 两次只输出“未执行的工具调用标记”）。被审的 v1.6.5 代码里本来就有 `launchctl bootstrap gui/…`（install-service 恢复原服务那段）。模型把这段代码原样带进工具调用参数，就命中了“写入开机自启”，于是整条回复被替换、节点被隔离。

所以用户的感受是对的：**命中的是 Agent 自己发出去的内容被模型回显**，不是中转站塞进来的东西。机制上是回复方向的检查，效果上等于拦了自己人。

### 1.3 有没有导致今晚 DSH 失败

- **没有直接导致审查失败**：第 37–39 轮验收库里，AGY 284 次、DSH 99 次、Qoder 202 次调用，没有一条回复是被替换后的拦截提示。今晚 DSH 三次卡住，Key 池记录都是上游不出首包（见 `DSH接入调查-20261023.md`）。
- **有间接影响**：监看中心日志只记“解除隔离”。今晚解除过 3 次：21:23 解除“积分服务”和 13007896054，23:59 解除 17095331892（对应 23:50 那次）。这些节点正是 Key 池给 DSH 分配的节点，隔离期间 DSH 能用的节点变少。隔离发生在几点、因为哪条规则，**查不到**：安全事件只存在代理内存里，00:17:22 Key 池代理重启后全部清空。过去被隔离过的节点见监看中心日志，10-13 以来解除了 15 次。
- 23:50 那次请求不是第 39 轮发的（第 39 轮 23:18 已停）。同时段机器上有别的会话在驱动 DSH（`/tmp/dsh-probe/drive4.py`）。

### 1.4 统计

拦截、告警、打码次数只在内存里，代理重启（00:17:22）后归零，现在是拦截 0、告警 0、打码 0、已检查 1。重启前的数字已经没了。这本身就是一个问题：出了事查不到。

## 2. 改造方案（等用户定）

方向：**把力气放在上游回传上**，请求方向默认不拦；拦截时要分清“中转站塞进来的”和“我自己发出去被回显的”。

| # | 改什么 | 理由 | 测试计划（每条都要在旧代码上失败） |
|---|---|---|---|
| 1 | **回显不拦**：工具调用里命中高危规则的片段，如果**原样出现在本次请求里**（被审代码、上下文），降为告警，不替换回复、不隔离节点 | 中转站篡改的特征是请求里没有、回复里冒出来；回显自己的内容不是篡改。直接修掉 23:50 这类误伤 | 请求里带 `launchctl bootstrap gui/501 x.plist`、回复工具调用回显同一串 → 放行、只告警、节点不隔离；请求里没有、回复里出现 → 照旧拦截并隔离 |
| 2 | **新增隐藏内容检测（回复方向，文字和工具参数都查）**：零宽字符（U+200B–200F、U+2060–2064、U+FEFF）、方向控制符（U+202A–202E、U+2066–2069）、Unicode 标签字符（U+E0000–E007F）、ANSI 转义序列 | 用户说的初衷：上游藏不可见字节让 Agent 读到并照做 | 回复文字里夹零宽字符、标签字符拼成的指令 → 告警，并按设置剥除或拦截；正常中文、emoji、代码不误伤 |
| 3 | **指令注入的文字检测（回复方向，先只告警）**：比如“忽略之前的指令”“你现在是…”、伪造的 system/assistant 角色块、在回复里冒充工具结果 | 先观察误报率再决定要不要拦 | 典型注入样例 → 告警；审查报告里引用这些词的正常文字（比如讨论注入）的误报率要先统计 |
| 4 | **安全事件写进文件**：拦截、告警、打码、隔离和解除隔离都追加到 `logs/keypool-security.jsonl`（只有规则名、节点、时间、打码后的片段） | 这次就是因为只在内存里，重启后查不到 | 触发一次拦截后重启代理，记录还在；文件里不出现明文密钥 |
| 5 | **隔离只用于高置信的篡改**：回显、未声明工具、只告警的规则都不隔离；隔离的原因写进节点状态，页面能看到 | 少把可用节点弄没 | 回显命中不隔离；非回显高危命中照旧隔离 |
| 6 | **请求方向**：默认只告警不改？见下面单列的利弊 | — | — |

### 请求密钥自动打码要不要保留（单列利弊）

- 保留的好处：Agent 不小心把真实密钥（私钥、云厂商 Key、Key 池自己的 Key）带进请求时，中转站看不到明文。这是唯一一道防止密钥流到第三方的关。
- 保留的坏处：会改动请求内容。审查代码、讨论配置时，像密钥的字符串被换成 `…[已打码]…`，模型看到的不是原文，可能误判。其中 `.env` 赋值和 `Bearer` 两条最容易命中正常代码和文档。
- 建议：
  - 强特征的照旧打码：私钥块、AWS/GitHub/Slack/OpenAI/Google 等带固定前缀的 Key、Key 池自己的 Key。
  - 弱特征的改成只告警、不改内容：`.env` 赋值、`Bearer`。
  - 页面上给两档开关。最终由用户选。

## 3. 影响与顺序

- 全部在监看中心（`工具/小八监看`），不在发布包里，**不影响 v1.6.5**；改完需要用户重开一次监看中心生效。
- 建议顺序：先做 4（落盘，零风险）和 1（回显不拦，直接消除误伤）→ 再做 2 → 3 先只告警观察几天 → 最后按用户选择调整请求方向的打码档位。
- 每一步单独可回退：都是 Key 池代码里独立的判断分支，加开关，默认值按用户定的来。

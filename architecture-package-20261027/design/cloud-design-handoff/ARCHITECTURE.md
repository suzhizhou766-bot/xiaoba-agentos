## 1. 总边界与角色

小八工作体系包含规则、第二大脑、AgentOS 核心、共享技能、工具、资产、审美与经验积累。AgentOS 是其中的任务、审计、审核和发布基础设施，不等于全部小八，也不等于某个宿主 Agent。

| 角色 | 责任 |
|---|---|
| 用户 | 目标、授权、成品验收、经验初审与终审、发布、付费、删除及生产切换 |
| 宿主 Agent | 读取规则与原文、理解任务、匹配能力、实际执行、集成后台贡献、验证、交付和记录 |
| AgentOS 核心 | 发布信任链、消息路由、任务队列、调用编排、预算、租约、回执、审计、经验状态机 |
| 独立后台 | 分工贡献或独立审查；只有可追溯的实际运行能形成后台证据 |
| 确定性裁判 | 按本地规则评分和选择回答；语义正确性仍需独立审核和实际验收证据 |
| 监看与裁决中心 | 展示状态与待审材料，承载用户裁决；与 Worker 使用一致配置 |

## 3. 信任链与接单

稳定 xiaoba 入口 → 读取发布索引 → 校验不可变发布全部文件 → 加载同一发布的 CLI → 配置/源码绑定核对 → 路由与执行。Worker 执行已绑定发布，不直接执行工作区候选源码。

日常任务在私人助理直接做，不因普通任务自动调用 session-start。只有完整口令“上班了小八助理”触发上班；本地 doctor 与真实后台探针分开。日常宿主任务不应被双后台事件链故障阻断，源码层彻底解耦仍属后续融合工作。

路由包括 direct（宿主直接处理）、agentos_multi（双后台任务）、review（用户审核）、ask_user（必要澄清）。当前授权和用户最新确认优先于旧技能说明。

## 4. 执行与独立审核

模块架构（本次用户确认，运行改造待实施）：已审核后台插件池 → 外部本次任务审查计划 → 通用双审协作引擎 → 各参与者独立执行 → 输出/身份/回执核验 → 按本次策略汇总 → 审计或经验结算。

| 对象 | 内容 | 模块内不设置 |
|---|---|---|
| 后台插件注册表 | 插件接口、能力、依赖、健康入口、实现指纹与真实身份来源 | 固定主审/备用身份、固定客户端名单 |
| 本次任务审查计划 | 外部选择的参与者引用、独立性和数量要求、权限、预算与替换策略、输入/产物摘要 | 内置默认参与者、模型或固定主备组合 |
| 通用双审协作引擎 | 调度、执行权、独立结果、回执核验、策略判定与审计 | 按后台/厂商名字分支、未知后台默认落到已有驱动 |

双审任务由外部策略表达需要两份独立审查，数量、预算、并发与接替条件均由已授权策略传入；模块不另外写固定值。模型来源、客户端命令、设置路径和特殊错误解析归插件，凭据由客户端持有，小八不擅改账号、模型或上游。

分工与审核分别有任务计划：collaborate → 参与者贡献与回执 → 宿主实际集成并测试 → 新集成证据 → 独立选择审核参与者 → collaborate-review。贡献者与审查者不要求同一完整名单，但必须核验真实工作、集成产物与本次审核证据。未知插件、能力不足或缺计划时明确报错，不能默认使用原来的任何一家。

用户可在新任务自由更换合格后台；进行中的任务换人形成新计划版本，保留旧来源、旧失败与替换原因。不能重贴旧 PASS、通过别名把同一实际来源算成独立意见、或通过换人抹掉实质 FAIL。

现有候选源码残留（历史实现诊断，不是模块目标）：仍有具名 AGY/DSH 默认组合、仅 Qoder 备用、驱动白名单、工作/审查名单相同要求和发布切换具名集合。这些尚未修改；逐文件解除点及验收见 `工作区/小八融合迭代-20261022/后台双审无绑定契约-20261027.md`。正式生产配置与包外发版审查证据分别保留。

## 5. 现有等待、故障与恢复约束

以下是当前共享策略和运行实现的约束；新模块按外部策略引用，不在双审模块内另加固定阈值或后台组合。解除运行代码绑定仍须同批核对这些读取方。

常规任务没有 300 秒总时长截止；连续 300 秒无可观察实际进展才判卡住。有效流增量和阶段推进刷新计时；PID、心跳、续租、重复初始化与 stderr 字节不刷新。

Worker 按 task attempt 核对执行权并续租；失去租约时停止旧 CLI 进程组，不替新执行者补位或结算。进度回执仅保留安全元数据，不能算最终结果。

外部限流、额度、网络、容量故障分类记录并有限退避；认证故障不自动重试或换账号；输出上限耗尽停止原样重发并提示拆分。补位必须核验故障来源，内部任务降级、未知或过期健康不能冒充真实探针失败。

单侧故障保留成功结果、回执及冻结证据。健康恢复不自动解冻；用户带 freeze-hash 显式恢复，只补失败侧。自动同伴诊断、自动修复、Headroom 重启与接管均已退役。

## 7. 交付与经验完整闭环

原有交付口令：用户说“交付”后，一次交齐交付记录、新经验候选、踩坑、打法、偏好。本次用户确认该口令视为本次成品已验收，验收须绑定实际任务和成品版本；关于口令的引用讨论不触发。

新经验 → 用户初审 → 待验证索引〔待实现〕 → 后续相似真实任务检索并核对适用条件 → 实际应用、记录执行与独立评分 → 用户说“交付” → 证据与评分自动回写原卡〔待实现〕 → 人工终审 → 敏感检查与索引复验 → 正式经验。

新任务同时产生的新经验仍从初审开始，旧经验验证不重复建卡。仅被检索或阅读不算实际应用。匹配分、回答排名分不能冒充验证分。终审显示实际效果、应用位置、各审查者评分理由、分歧及适用范围。具体量表未定，不杜撰评分阈值。

类型分流：audit 仅结算审计；rule 依据用户明确偏好或规则，两次人工裁决；method 初审后需要真实执行和独立验证再终审。真实任务证据如何接入现行隔离试验门禁仍需同批实现与验证，本次设计不自动撤销现行门禁。

两次经验批准绑定同一候选哈希。正文或初审变化使不匹配的旧验证失效；最新失败/未完成不能被旧成功覆盖。重复交付、重试和并发只结算一次。未经终审的候选不进入正式长期记忆，不增加正式经验成功复用计数。

已发布经验继续复用、对账和复验；连续失败达到现行阈值 2 时退役并保留私有归档，重新启用仍需受控流程。

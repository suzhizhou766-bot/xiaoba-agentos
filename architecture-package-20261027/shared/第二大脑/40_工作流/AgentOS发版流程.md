# AgentOS 发版流程（版本发布与升级）

任何 Agent 给小八 AgentOS 做版本升级时照这个流程走。

相关检索词：发版、发布、升级、发布升级、版本升级、版本发布、上线、切换、候选、验收、下一版、v1.5.2、盘点、漏掉。

它来自 v1.5.1 的实际发布（2026-10-10）；用户要求写进第二大脑，为的是换一个 Agent 来发版时不再漏掉别的 Agent 建的东西。

## 为什么有第一步

v1.5.1 发版时漏了“小八审美手册”：它是另一个 Agent 在 `私人助理/审美提升/` 建的，资料齐全，但没有登记进通用入口、技能索引和发布生成的第二大脑树。负责发版的 Agent 只按登记页上的清单收拢范围，没有去看有没有“已经建好但没登记”的东西，于是发布之后别的 Agent 仍然不知道它存在。用户发现后才补了入口。

结论：发版的范围不能只来自待办清单，还必须来自一次实地盘点。

## 第一步：盘点（在确定这一版做什么之前）

1. 读 `私人助理/工作区/README.md` 的“下一版待办”。
2. 实地看有没有建好但没登记的东西，至少查这几处：
   - `私人助理/` 顶层的每个目录；
   - `私人助理/工具/` 下的每个工具；
   - `私人助理/skills/` 下不是链接的实体文件夹；
   - 各 Agent 的私有目录：`~/.codex/skills/`、`~/.gemini/config/skills/`、`~/.claude/skills/`、`/Users/suzhizhou/Documents/Codex/` 下带日期的输出目录；
   - 第二大脑“70_复利规则/经验”里上一版之后新发布的笔记：标题像“某某资料入口”“某某模块”的，往往对应一个新建的目录。
3. 对查到的每一样，核对它在下面四处有没有：
   - `私人助理/AGENTS.md` 第 3 节的模块清单；
   - 第二大脑的入口笔记（能力放“20_能力与技能”，方法和知识放“30_方法与知识”）；
   - 技能索引（`xiaoba skill-match` 能不能按任务匹配到）；
   - `私人助理/系统/小八工作体系/registry.json`。
4. 把“已建好但没登记全”的列成清单交给用户，逐项问：进这一版、放下一版，还是不接入。不要替用户决定，也不要因为清单上没有就默认不做。
5. 用户的答复写进 `私人助理/工作区/README.md`，再开始做候选。

## 接入一样东西的验收

登记完要实测，不能只看文件写进去了：

- `xiaoba memory-retrieve` 用它的名字能查到；
- `xiaoba skill-match` 用任务式的说法能匹配到（例如“帮我调色”“做一个网页”），只用名字能查到不算；
- 从根笔记逐层点进去能走到它。

每天都在改的文件不要放进带哈希绑定的索引（技能索引、价值文件索引），否则一改自检就失败；绑定的应该是一份稳定的指路文件。

## 先判断要不要发版

- 改第二大脑里“能力与技能、方法与知识、工作流、资产与索引”四个分支下的笔记：不发版。直接改，改完按 AGENTS.md 的命令重建并校验笔记索引。技能卡和价值文件索引这 9 篇由 `xiaoba content-notes-sync` 从索引生成，不要手改由索引决定的那一段；在那一段后面追加的内容会被保留。
- 改规则类笔记（根笔记、治理与裁决、当前上下文、复利规则下的门禁与入口、版本历史）：要发版。它们仍由发布生成，直接改会挡住下一版。
- 改技能（自 v1.6.1）：不发版，但不能就地改。把技能目录拷到 `私人助理/skills/` 之外当草稿，在草稿里改；`xiaoba skill-review-prompt <技能名> --draft <草稿目录>` 生成审查说明，`xiaoba submit` 提交给两个后台；都通过后 `xiaoba skill-publish <技能名> --draft <草稿目录> --review-task <任务编号>`。
- 改价值文件（自 v1.6.1）：不发版。改原文或 `私人助理/系统/价值文件索引/catalog.json` 后运行 `xiaoba knowledge-index-rebuild`。
- 改运行代码、脚本、配置：要发版。

## 发版的档位（自 v1.5.6）

档位由工具按改动的文件路径算，不由 Agent 判断；只能由人调高。查看某个候选的档位：

```sh
/usr/bin/python3 scripts/release_tier.py <线上当前发布包>/agentos <候选源码根>
```

- 补丁：只改文档，或只改独立的、不带底线标记的测试。不过两个后台，构包时自己实跑全量测试。
- 常规：改了运行代码、脚本、配置、技能、入口技能卡；或改了带底线标记的测试、测试夹具和共用测试代码、标记清单、分档规则。两个后台各自独立通过。
- 迁移：数据库结构版本、部署步骤、数据契约版本、顶层目录有变化，或结构指纹文件变了。走全套，包括复制现场演练。
- 改了切换脚本、笔记合并规则这类一旦出错就伤到线上的东西，即使工具算出常规档，也要做复制现场演练。

## 后面的步骤

最近一版的全部脚本和记录在 `私人助理/工作区/小八AgentOS-架构第3步/`（`work/` 下有准备元数据、冻结与构候选包、跑双审、建演练现场、跑演练、构正式包的脚本；`当前状态.md` 是汇总）。顺序是：

1. 在 `私人助理/工作区/` 下建候选目录，不改线上文件；能写成任务卡的工作派给辅助模型，主力核对回执。
2. 测试全过、清单重建之后，尽量一次定稿再进验收：候选只要再改一个字，所有审查都要重跑。
3. 建沙箱，两个后台各自独立审查，每一份都要两个后台通过。后台判不通过时先自己复现，成立就改。提交给后台的说明里不要写上一轮的结论。
4. 构建正式包（`--previous-release` 指向线上当前发布包）。
5. 需要演练的版本：在复制现场上逐阶段注入故障确认能退回，再成功切换一遍。
6. 主力用包里的切换命令对线上跑只读计划。
7. 第 5、6 步都通过之后，才把预检和切换两条命令交给用户。切换由用户在自己的终端执行。v1.5.6 就是因为命令给早了，没做演练就切换了。
8. 切换后：主力独立只读回验（两处入口、Worker 进程编号变了且指纹与磁盘一致、自检）；运行 `xiaoba content-notes-sync`；重新开启监看中心；把这项工作从工作区的进行中页面移除，遗留问题写成下一版待办。
9. 用户说“交付”时再做交付记录。

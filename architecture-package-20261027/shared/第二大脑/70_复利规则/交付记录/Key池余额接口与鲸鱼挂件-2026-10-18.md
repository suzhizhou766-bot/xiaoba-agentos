# Key 池全池余额接口：让 DSH 鲸鱼余额挂件读到 Key 池余额（2026-10-18）

用户于 2026-10-18 说“收尾交付”。本记录是这一段对话的交付总结，由宿主（Claude Code）的一个分出会话整理。

## 用户要什么

DSH 现在通过自定义 provider“小八并发”走 Key 池。用户想让 DSH 里装的第三方余额挂件（GitHub `Witherwithwinter/DeepSeek-Balance-Whale-Widget-Bowl`，包名 `dsh-whale-widget-bowl`，v0.5.0，MIT 许可）显示 Key 池的余额和使用详情。

## 调研结论

- Key 池原本就有余额规则（`monitor_core/keypool_balance.py`，2026-10-01 起）：用站点网页会话（Session Cookie + TF-User）按节点查，结果只放在监看中心内存里，并推给 8780 代理用来切换线路。原来没有全池合计的接口，也没有兼容 DeepSeek 格式的接口；8780 收到不认识的路径会转发给某一个节点。
- 插件：内置的 DeepSeek 只认 `https://api.deepseek.com/user/balance`。另有「自定义 HTTP」模板，可以填接口地址、`Bearer {key}`、JSON 字段路径；必须配一个凭据；除 Authorization 外不能加别的请求头（所以直接查 tierflow 网页接口这条路走不通）；地址指向本机要勾「允许把凭据发送到自定义地址」。本机 `~/.dsh/profiles/desktop/node_modules/dsh-whale-widget-bowl` 和 GitHub main 逐字节一致。
- 插件的“每轮消耗、按模型明细”来自 DSH 自己的会话事件，与 provider 无关，本来就能用；“今日已用”在有余额接口时按余额下降算。

## 交付内容

- 8780 代理新增 `GET /user/balance`（`/v1/user/balance` 也行）：要 Key 池主 Key；由代理自己回答，不转发、不进用量统计；格式同 DeepSeek 官方，`total_balance` 是全池合计（元），`granted_balance` 是套餐部分，`topped_up_balance` 是按量部分，另带 `key_pool` 说明读数覆盖了几个启用节点。只算启用节点 10 分钟内的读数；没有读数返回 503。
- 改动在监看中心仓库提交 `f6c1951`：`monitor_core/keypool_proxy.py`、`tests/test_keypool.py`（新增 3 个测试）、`README.md`（“余额查询”后补了一条说明）。先在草稿副本里改和测，用户看过之后才上线。
- 插件表单填法：厂商模板选「自定义 HTTP」（不能用 OpenRouter，它自带的总量、已用字段会留着），币种人民币，凭据名另起（如 `XIAOBA_KEYPOOL_KEY`），API key 由用户自己粘贴 Key 池主 Key，余额接口 `http://127.0.0.1:8780/user/balance`，余额字段 `balance_infos[0].total_balance`，勾选「允许把凭据发送到自定义地址」。

- 草稿副本和线上各跑一遍：草稿里 Key 池 116 个测试通过；线上 `test_keypool`、`test_keypool_balance`、`test_keypool_stats` 共 139 个测试通过（macOS 自带 Python 3.9）。

## 已知限制（已告诉用户）

- 挂件的“今日已用”按余额下降算，是整个 Key 池所有客户端、所有账号的花费，不只是 DSH；充值、续套餐时余额上跳，插件不计为消费。
- 监看中心没开时接口返回 503，挂件会显示查询失败。
- 插件“事件匹配”建议填 `deepseek-v4.1-flash`，这是从 Key 池用量记录里客户端要的模型名推断的，没有核实 DSH 会话事件里的名字。单价留空时按 DeepSeek 官方 Flash 价估算。

## 过程中纠正的

- 宿主让用户不带 Key 用 curl 测接口，说“看到 401 说明请求被代理自己接住了”。这个说法是错的：不带 Key 的请求，新旧代码都会在认证这一步返回 401。后来改为用存储的主 Key 在本机验证，结果正常。用户带 Key 测时也拿到 401，原因是 Key 不对，不是接口的问题。

# 按任务卡分工发布 v1.5.1 的经验

来源：2026-10-07 至 2026-10-10 的对话，宿主 Claude Code 整理。以下每条都有当次的实际结果作依据；没有验证的单独标出。

## 分工

- 主力先拆卡再动手。这次第一批工作里，修预审问题、升版本号、写发布说明、改写上一版的沙箱脚本，本来都可以写成卡，主力却自己做了；用户随后明确要求“能交给他们三个的工作你就不要亲自动手”。
- 任务卡的固定内容：目标、只允许改的文件、限制、验收命令和期望结果、停止条件、回执格式。几张卡同时进行时，文件名单互不重叠，并在每张卡里写明另一张卡正在改哪些文件。
- 卡里的验收命令先在草稿副本里预演一遍。这次预演发现 `python -m unittest tests.x` 的写法在这个仓库会报错，改成 `discover -s tests` 后才发出去。
- 模型分配的实际结果（各一次，不构成排名）：Qwen 3.8 Max 做需要读懂上下文的修复和高风险脚本起草，回执里主动指出了任务卡写错的一处；DeepSeek V4.1 Flash 做边界清楚的替换和小修复，三次都一次通过；Gemini 3.8 Flash 做只读预审，提出的 6 处问题核对后全部成立，但回执里写的几个函数名与实际不符，脚本本身是对的。
- 回执不能直接信，主力要看实际改动。核对方法：看改动是否只落在允许的文件里、把替换类改动反向还原后比对、把缺陷场景自己重跑一遍。

## 验收

- 同一份审查材料，同一个后台两轮结论可以不同。A 部分的材料第一轮 dsh_review 判通过，第二轮内容一字未改却审出一个真实缺陷。单轮通过不代表没有问题。
- 验收证据绑定同一份源码清单，候选只要改一个字，四份审查就要全部重跑。这次三轮，每轮约 15 分钟。所以候选要尽量在第一轮之前就定稿，包括文档里的措辞。
- 审查材料生成脚本里不要写死会随候选变化的数字。脚本里写死的“修改 28 个文件”与按清单算出的 29 并排出现，发出前被发现并改成按清单计算。
- 后台审出的问题先自己复现再处理。这次两轮不通过的意见都成立：一处是版本说明里前后两句自相矛盾（上一版就有），一处是自动生成的候选会叠出两个一级标题。

## 切换

- 本会话的安全检查不允许宿主执行切换脚本，连同一条命令里的只读检查也被拦。实际做法：用户在自己的终端里依次执行关闭监看中心、只读预检、正式切换三条命令，宿主负责切换前的准备和切换后的收尾。
- 涉及目录改名的发布，切换后自检会先有一项不通过：数据库里已发布经验的记录路径还指向旧目录。运行不带 `--dry-run` 的 `memory-rename-notes` 后恢复。带 `--dry-run` 只预览，不写库。
- 切换脚本把可回退的动作（三处改名）放在不可回退的动作（覆盖线上源码）之前，并在预检里检查新名字没有被占用。

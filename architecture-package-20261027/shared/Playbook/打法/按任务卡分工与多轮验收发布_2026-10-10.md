# 按任务卡分工与多轮验收发布（2026-10-10）

来源：小八 AgentOS v1.5.1 发布。适用于“主力 Agent 带几个辅助模型做一次发布”的场景。记录在 `私人助理/工作区/小八AgentOS-v1.5.1/`。

## 一、先拆卡，再动手

1. 接到活先问：这一块能不能写成任务卡。能，就在开工时拆出去，不要自己做到一半再分。
2. 主力只留四类：核对回执；要花后台额度或动线上的步骤；需要用户点头的决定；小到写卡比动手还费事的改动。
3. 一张卡的固定内容：目标、只允许改的文件、限制、验收命令与期望结果、停止条件、回执格式。
4. 几张卡同时进行时，文件名单互不重叠，并在每张卡里写明别的卡正在改哪些文件、碰到那些文件的测试失败只报告不修。
5. 卡里的验收命令先在草稿副本里跑一遍，确认照做能过再发。
6. 给用户的转发内容是一段可以一键复制的短文字，只写“读取并执行哪张卡”，卡的正文放在文件里。

## 二、按模型分配

- 需要读懂上下文再下手的修复、风险高的脚本起草：Qwen 3.8 Max。
- 边界清楚、机器能验收的替换和小修复：DeepSeek V4.1 Flash。
- 只读预审、按模板改写脚本：Gemini 3.8 Flash。

以上是这一次的分配和结果，不是定论。

## 三、核对回执

1. 先看改动落在哪些文件，是否都在允许的名单里。
2. 替换类改动：把替换反向还原后与原文比对，确认没有别的变化。
3. 修复类改动：把缺陷场景自己重跑一遍，不只看对方说的测试数。
4. 回执里的说明可能与实际不符（函数名、测试名写错），以文件为准。
5. 回执里“没做或不确定的”要逐条看，那里常有任务卡本身的错。

## 四、验收

1. 候选在第一轮验收之前尽量定稿，文档措辞也算；候选改一个字，所有部分都要重跑。
2. 每轮：重建清单、提交、归档上一轮证据、重建沙箱、初始化、自检、实测两个后台、重新生成审查材料、提交审查。
3. 后台判不通过时，先自己复现。成立就改，属于代码改动就派卡；不成立再考虑改材料。
4. 一轮全部通过才构建正式包，再跑切换脚本的只读预检。

## 五、切换

1. 用户同意后，由用户在自己的终端执行三条命令：关闭监看中心、只读预检、正式切换。每条单独给，写明成功和失败各是什么样子。
2. 宿主做收尾：替换文档里的旧名字、改名预览给用户看、用户确认后正式改名、复查自检、重新开启监看中心。
3. 做完把这项工作从 `工作区/README.md` 的进行中页面移除，遗留问题写成下一版待办。
